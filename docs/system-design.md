# System Design — red_planet

Живой документ по архитектуре. Движок: **Godot 4.7 (.NET) + C#**, платформа — только десктоп.

Здесь зафиксировано: где какие слои, что делать нодой, что держать просто в памяти, как связывать сущности и как ужимать журналы, не ломая проекции. Примеры кода — реальные, из проекта, а не наброски: имена классов и методов совпадают с тем, что лежит в `scripts/`.

---

## 1. Философия

В основе — модель метаданных 1С, перенесённая на игру. Почему она уместна для стратегии-базостроя: **экономика базы по своей природе и есть учёт.** Добыча, производство, стройка — документы; запасы и население — регистры; типы юнитов и зданий — справочники.

**Но в коде используется словарь event sourcing и CQRS, а не 1С.** Причина простая: `Register` в английском не значит «регистр накопления» — это либо глагол, либо регистр процессора, отсюда рождались уродцы вроде `RegisterRegistry`. Общепринятые термины понятны и человеку, и ИИ-агенту, и совпадают с любой статьёй по теме.

| 1С (мысленная модель) | В коде | Известный паттерн |
|---|---|---|
| Справочник | `Catalog` + `…Definition` | data-driven определения (`.toml`, собирает `ContentCompiler`) |
| Документ | `IEventRecord` | event sourcing — иммутабельная запись о факте |
| Регистр накопления | `Projection` | CQRS read model — производный агрегат |
| — | `GameSystem` | логика над мини-ECS |

**Ценности, под которые оптимизируем** (они диктуют решения ниже):

1. Точечный контроль хода исполнения — свой планировщик, а не неявный обход дерева нод.
2. Наблюдаемость зависимостей — единый композиционный корень.
3. Конфигурируемость под геймдизайн и DX — настройка данными и в редакторе (`.toml`, `[Export]`, сигналы).
4. Производительность — по мере необходимости, не догма. Но инкрементальность закладываем сразу.

**Чего пока НЕ делаем:** сети и мультиплеера, DI-фреймворка, детерминированного lockstep, сохранений.

## 2. Соглашения об именовании

Правило одно: **абстракция носит имя паттерна, конкретный тип — имя из предметной области.**

- `IEventRecord` → `ResourceSpent`, `OreDepleted`, `BlueprintPlaced`
- `Projection` → `StockpileProjection`
- `WorkNode` → `Blueprint`

Отсюда следуют два частных случая, которые выглядят непоследовательно, но таковыми не являются:

- **У документов суффикса нет.** Прошедшее время само выдаёт природу типа: `ResourceSpent` ни с чем не спутать. `ResourceSpentEvent` — шум.
- **У проекций суффикс есть.** `Stockpile` — обычное существительное, грамматического признака в нём нет, без суффикса тип читался бы как «просто склад».

**Суффикс `Store` = типизированный контейнер с поиском по ключу.** Три штуки, различаются только ключом:

| Контейнер | Ключ | Что хранит |
|---|---|---|
| `EventStore` | тип документа | потоки документов |
| `ProjectionStore` | тип проекции | проекции |
| `EntityStore` | `EntityId` | живые ноды |

`Catalog` из этого правила выведен намеренно: `Store` — про изменяемое состояние игры, а каталог — статический контент, загруженный один раз.

**`Index` — не четвёртый `Store`, и суффикса не носит.** У хранилища один ключ и один ответ на объект; у индекса ключей столько, сколько разрезов над множеством спросили. Разные вопросы — разные имена.

## 3. Слои и поток данных

- **Справочник** (`Catalog`, `UnitDefinition`, `ToolDefinition`) — статические определения. Файлы `.toml` → память.
- **Документ** (`IEventRecord`) — факт. Живёт в журнале в памяти.
- **Проекция** (`Projection`) — производный агрегат, обновляется дельтой.
- **Система** (`GameSystem`) — логика. Нода со свойствами `[Export]`.
- **Сущности** — видимое/физическое это ноды, их данные — обычные C#-объекты.
- **Индекс** (`Index`) — множество объектов и разрезы над ним по признаку и по ключу.
- **Планировщик** (`Scheduler`) — порядок систем и фазы кадра.
- **Фабрика** (`Spawner`) — единственное место, где рождаются сущности.
- **Корень сессии** (`GameManager`) — держит всё перечисленное. Нода в сцене сессии, не автозагрузка.
- **Площадка** (`Playground`) — мир: все видимые сущности, разложенные по слоям отрисовки.
- **Контент** (`Content`) — единственная автозагрузка: справочники и прочее, что живёт дольше сессии.

Поток за один физический шаг симуляции:

```
намерение (игрок или ИИ)
   → система проверяет и дописывает ДОКУМЕНТ в EventStore
      → ПРОЕКЦИЯ впитывает его дельтой прямо в момент дозаписи
      → системы РЕАГИРУЮТ на документы кадра (спавн, эффекты)
   → cleanup: Index.Sweep и ClearTransient — только в физическом цикле
```

Отдельно планировщик гоняет системы графического цикла (`UpdateCycle.Process`) из `_Process` корня — для представления, которое должно совпадать с отрисовкой (сейчас это `CursorSystem`, затем `CommandSystem` и `HoverSystem`). Отрисовка нод по-прежнему в их собственном `_Process`.

Ключ развязки: **системы не дёргают друг друга напрямую — они общаются через документы.** Система приказов не знает про мир: она дописывает `BlueprintPlaced`, а кто отреагирует — её не касается.

## 4. Дерево сцены и где что живёт

### 4.1 Три ветки сессии

Дерево режется по одному правилу: **что умирает вместе — живёт вместе.**

```
Root (Node)                     ← приложение: живёт от запуска до выхода
├── MainMenu (CanvasLayer)      ← либо меню…
└── Session (Node2D)            ← …либо сессия. Одновременно — только одна ветка
    ├── Systems (GameManager)   ← журнал, проекции, индекс, сетка, порядок кадра
    │   ├── CommandSystem
    │   ├── PlayerAiSystem
    │   └── …
    ├── Playground (Node2D)     ← мир, разложенный по слоям
    │   ├── Terrain  → Grid
    │   ├── Deposits
    │   ├── Structures
    │   ├── Actors
    │   ├── Projectiles
    │   └── Effects
    └── View (Node2D)           ← наблюдатели
        ├── Camera (CameraRig)
        ├── Hud             — счёт боя, подсказки и пауза, слева вверху
        ├── ResourceBar     — метал, производительность, энергия; сверху по центру
        ├── SelectionPanel  — состав выделения, слева внизу
        ├── HoverPanel      — справка о сущности под курсором, ярусом выше выделения
        ├── CommandPanel    — доступные приказы, справа
        ├── Buildbar        — строительная панель, внизу по центру
        ├── ControlGroupBar — полоса боевых групп, у самого низа
        └── PauseMenu (слой 10)

Content (автозагрузка)          ← справочники: переживают любую сессию
```

**Меню и сессия взаимоисключающи.** При открытом главном меню сессии в дереве нет вовсе, а вместе с нею нет ни журнала, ни проекций, ни единой сущности мира. Это то же правило, что и выше, доведённое до конца: выход в меню и есть удаление сессии, поэтому «начать заново» ничем не отличается от первого запуска. `Root` переключает ветки методами `NewGame`, `OpenMainMenu`, `RestartSession` и `QuitGame`, а состояния между ними не хранит.

**Почему GameManager больше не автозагрузка.** Автозагрузка живёт столько же, сколько приложение, и для справочников это верно, а для сессии — нет. Пока менеджер был ею, журнал, склад, сетка занятости и счётчик идентификаторов переживали пересоздание сцены, тогда как системы и мир рождались заново: первый же перезапуск затащил бы в новую игру занятые клетки и призраков прошлой. Теперь срок жизни состояния равен сроку жизни мира, который его породил, и снос сессии — это `RemoveChild` одной ветки.

**Порядок веток значим.** `Systems` идёт первым, чтобы планировщик и разрезы собрались раньше, чем проснётся хоть один объект мира; `View` — последним, потому что ему нужно готовое состояние. Сам `Session` просыпается после всех детей, поэтому стартовая раздача (база, коммандер, начальный запас) делается именно там.

**Направление зависимостей.** `View` читает `Systems`, но не наоборот; `Playground` не знает ни о том, ни о другом — он лишь контейнер. Тем самым ветка мира и ветка вида заменяемы поодиночке: сетевому клиенту достанутся они, серверу — `Systems`.

Пересборка сессии висит на `F5` (`Root.RestartKey`) — это не удобство, а проверка: если после перезапуска в мире всплывает что-то из прошлой игры, значит, состояние опять утекло за границу сессии.

### 4.2 Пауза

Состояние паузы хранит `Session`, а меню лишь отражает его и просит изменить, поэтому клавиша, кнопка на HUD и вызов из кода не могут разойтись.

Останавливается **только ветка `Systems`**: ей выставляется `ProcessMode.Disabled`, и этого достаточно, так как и физический, и графический циклы планировщика зовутся из колбэков композиционного корня. Заодно к системам перестаёт поступать ввод — на паузе нельзя ни отдать приказ, ни поставить постройку, причём безо всякой отдельной проверки.

Почему не `GetTree().Paused`: остановка всего дерева заморозила бы и наблюдателей. Здесь же камера продолжает слушаться WASD и колеса, и поле боя на паузе можно осмотреть — для стратегии это осмысленно, а мир при этом стоит намертво.

**Меню паузы — отдельное дерево интерфейса,** соседнее с `Hud` и лежащее выше него по слою. Разделены они намеренно: HUD показывает состояние идущей игры, а меню паузы управляет самой игрой и обязано работать тогда, когда симуляция стоит. Сведи их в одно дерево — и видимость меню пришлось бы согласовывать с каждым элементом HUD по отдельности.

**Разбор Escape решается явно, а не порядком обхода дерева.** Клавишу ловит меню паузы и первым делом спрашивает `CommandSystem.CancelContext()`: пока есть что сбрасывать, Escape работает по-старому, и лишь на пустом месте открывает паузу. Сброс идёт по шагу за нажатие — сначала режим постройки, затем выделение: отменяя постройку, игрок не должен заодно терять отряд.

### 4.3 Деревья интерфейса

Интерфейс разбит не по картинке, а **по источнику данных**: одно дерево — один вопрос, на который оно отвечает. `ResourceBar` смотрит только на проекцию склада и баланс кадра, `SelectionPanel` и `CommandPanel` — только на состав выделения, `Buildbar` — на панели выделенных строителей, `Hud` — на счёт боя. Отсюда и разное поведение: полоса ресурсов висит всегда, три остальных появляются и исчезают вслед за выделением, и перестройка любой из них не задевает соседей.

Каждое дерево — свой `CanvasLayer` с корневым `UiFrame`, разметка собирается кодом. Панели, зависящие от выделения, держат **отпечаток** состава (строку из имён или идентификаторов) и пересобирают элементы только при его смене: перестройка на каждом кадре теряла бы наведение и нажатие.

**Группы выделения.** Здесь только суть; полный свод поведения — жесты, правила отбора, сброс, числа и их место — лежит рядом с кодом, в `scripts/units/selection.md`.

Рамка почти всегда захватывает лишнее — тянешь по отряду у базы и цепляешь генераторы, после чего приказ «идти» уходит в пустоту. Поэтому из пойманного рамкой остаётся только преобладающий род: у каждого свой вес, побеждает наибольшее произведение количества на вес, при ничьей — более тяжёлый род. Сейчас родов два: боты весом 1 (включая коммандера) и постройки весом 0,5, так что при равном числе верх берут боты, а две постройки перевешивают одного бота, но не двух.

**Рамка поверх уже выделенного добирает родню.** Преобладание судит только по улову и о намерении, высказанном первым щелчком, ничего не знает. Поэтому когда выделение не пусто, работает другое правило — лестница из трёх ступеней, от точного к общему:

1. в выделении один тип — добирается буквально этот тип;
2. разные типы одного рода — добирается весь род;
3. разные роды — добираются эти роды, и больше ничего не сужается.

Тип опознаётся по `DisplayName`, по той же строке, которой подписана панель выделения: показанное и отфильтрованное обязано совпадать. Отдельного ключа заводить не стали — `DefId` у юнита намеренно пуст, он служит учёту потерь и ёмкости хранилища.

У первой ступени есть цена: она теряется от одного случайного попадания. Зацепив к трём генераторам турель, игрок переходит на вторую ступень, и дальше рамка гребёт все постройки; возврат один — рамка без `Shift`, начинающая выделение заново. Принято сознательно, поскольку обратная крайность — фильтр строго по набранным типам — не давала бы добрать рамкой ни одного нового типа вовсе.

Оба правила применяются **только к улову рамки**. Одиночный щелчок — прямое указание на сущность, и спорить с ним нельзя: щёлкнув по генератору, игрок выделит генератор, сколько бы ботов вокруг ни стояло. Прежнее выделение не пересматривается никогда, поэтому смешанный отряд собрать по-прежнему можно — просто не случайно.

**Повтор по той же цели означает «и всех таких же».** `DoubleTap` считает двойным выбором только повтор по той же живой сущности, уложившийся в промежуток `CommandSystem.DoubleTapInterval` (настраивается в инспекторе, по умолчанию 0,35 с). Два быстрых щелчка по разным юнитам двойным выбором не считаются — иначе беглая расстановка приказов то и дело оборачивалась бы выделением половины карты.

Детектор **о мыши не знает намеренно**: внутрь передаётся только цель, а откуда взялся выбор — кнопка, палец, геймпад или горячая клавиша — его не касается. Второй источник двойного выбора добавляется без правки этого кода. Время берётся системное, а не игровое: двойной щелчок есть свойство руки игрока и от паузы или масштаба времени зависеть не должен.

Область не ограничена видимой частью: «выделить всех фабрикаторов» — приказ о составе отряда, а не о том, что попало в кадр, и результат не должен меняться от положения камеры.

### 4.4 Слои площадки

Порядок объявления `WorldLayer` и есть порядок отрисовки. Раньше эту роль исполняли `ZIndex`, расставленные вручную в трёх разных файлах (снаряд знал про шестёрку, призрак постройки — про десятку), и добавление нового рода сущностей сводилось к угадыванию свободного числа. Теперь слой выбирает `Spawner` — в единственном месте, где род сущности вообще известен:

```csharp
_gm.Playground.Add(WorldLayer.Structures, building);
_gm.Playground.Add(WorldLayer.Actors, unit);
_gm.Playground.Add(WorldLayer.Projectiles, projectile);
```

Слои задают лишь порядок. Чем именно рисуется кадр — растровые слои с шейдером, множественные
сетки, собственный `_Draw` сущности — описано в [rendering.md](rendering.md).

### 4.5 Нода, память или ассет

> **Нода — только там, где нужен движок:** отрисовка, физика, ввод, участие в дереве сцены, настройка в редакторе. Всё остальное — обычные C#-объекты в памяти под композиционным корнем. Так слой данных не зависит от Godot и тестируется без движка, а ноды остаются «кожей».

| Слой | Форма в Godot | Пример |
|---|---|---|
| `Root`, `Session` | **нода** | приложение и сессия: заводят и сносят ветки дерева |
| `MainMenu`, `Hud`, `ResourceBar`, `SelectionPanel`, `CommandPanel`, `Buildbar`, `PauseMenu` | **нода** (`CanvasLayer`) | деревья интерфейса, разметка собирается кодом |
| `GameManager` | **нода сессии** | держит журнал, проекции, сетку, планировщик |
| `Content` | **нода-автозагрузка** | справочники и всё, что переживает сессию |
| `Playground` | **нода** (`Node2D`) | контейнер мира со слоями отрисовки |
| `Scheduler`, `Spawner`, `WorldGrid`, `Index` | чистый C# в корне | порядок систем, создание сущностей, занятость клеток, разрезы |
| `EventStore` + документы | чистый C# в корне | `ResourceSpent`, `OreDepleted` |
| `ProjectionStore` + проекции | чистый C# в корне | `StockpileProjection` |
| Справочники | **`.toml`** + чистый C# | `UnitDefinition`, `ToolDefinition` — собирает `ContentCompiler` |
| Строительные панели | **`.toml`** + чистый C# | `BuildbarDefinition` — сетка с координатами |
| Системы | **нода** с `[Export]` | `OrderSystem`, `MetalSpotSystem` |
| Видимые сущности | **нода** (`Node2D`) | `Unit`, `Building`, `Blueprint` |
| Данные сущности | чистый C#, которым владеет нода | инвентарь, здоровье |
| Связи между сущностями | `EntityId`, не ссылка | документы носят id |
| Связь с представлением | **сигналы Godot** | соединяются в редакторе или в коде |

## 5. Слои подробно

### 5.1 GameManager — композиционный корень сессии

Одна нода держит всю инфраструктуру, а системы висят на ней детьми — так «система принадлежит менеджеру» перестаёт быть договорённостью на словах и становится фактом дерева. Как единая точка сборки менеджер делает зависимости видимыми, а не прячет их по углам.

```csharp
public partial class GameManager : Node
{
    public static GameManager I { get; private set; }

    [Export] public Playground Playground;      // сестринская ветка: мир сессии

    public EventStore Events { get; } = new();
    public ProjectionStore Projections { get; } = new();
    public Catalog Catalog => Content.Catalog;  // справочники живут дольше сессии
    public EntityStore Entities { get; } = new();
    public Index Index { get; } = new();
    public WorldGrid Grid { get; } = new();
    public Scheduler Scheduler { get; } = new();
    public Spawner Spawn { get; private set; }

    // Система по типу вместо рукописного свойства на каждую
    public T System<T>() where T : GameSystem => Scheduler.Get<T>();

    // Постоянные разрезы держим здесь же, где и проекции: состав производного
    // состояния должен быть виден в одном месте
    public KeySlice<Faction, IDamageable> Targets { get; private set; }

    public override void _EnterTree()
    {
        I = this;
        Playground ??= GetNodeOrNull<Playground>("../Playground");
        Spawn = new Spawner(this);

        Targets = Index.SliceBy<IDamageable, Faction>(target => target.Faction);

        // Порядок держим явным: если проекция читает другую, зависимость идёт раньше
        Projections.Add(new StockpileProjection());
        Projections.SubscribeAll(Events);
    }

    // Наш _Ready приходит после _Ready всех дочерних узлов — это и есть единственная
    // общая точка «все системы зарегистрированы», вторая фаза их инициализации
    public override void _Ready()
    {
        foreach (var system in new List<GameSystem>(Scheduler.Systems))
            system.Link();

        SystemsLinked = true;

        // Камера с приоритетом 0 обновляется раньше графических систем:
        // меньшие ProcessPriority Godot исполняет первыми
        ProcessPriority = 1;
    }

    // Сверка на текущего владельца обязательна: при пересборке сессии новый менеджер
    // встаёт на место раньше, чем удалится старый
    public override void _ExitTree()
    {
        if (I == this)
            I = null;
    }

    public override void _PhysicsProcess(double dt)
    {
        Scheduler.RunCycle(UpdateCycle.PhysicsProcess, dt);
        Index.Sweep();          // состав мира — только после физических систем
        Events.ClearTransient();
    }

    public override void _Process(double dt) =>
        Scheduler.RunCycle(UpdateCycle.Process, dt);
}
```

Регистрация и подписка разнесены на два шага (`Add` … `SubscribeAll`) специально: сначала собираем состав, потом подписываем — тогда проекции могут ссылаться друг на друга.

Площадка ищется в `_EnterTree` и находится там наверняка: дерево сцены создаётся целиком до того, как хоть одна нода в нём получит уведомление о входе.

### 5.2 Справочники — Catalog и `.toml`

**Одна сущность — один файл.** Бот, постройка и противник описываются общим `UnitDefinition`: разница между ними — набор заполненных секций, а не разные виды данных. Роль выводится из заполненного, а не задаётся признаком: занимает клетки — постройка, задана секция `[assembly]` — строится, есть строительная рука — умеет строить и чинить.

```toml
# resources/units/player/fabricator/fabricator.toml
id    = "fabricator"
name  = "Фабрикатор"
class = "bot"                     # какой C#-класс поднимет Spawner
tags  = ["mobile", "builder"]     # категории из resources/content/tags.toml
tools = ["fabricator_arm"]        # чем снабжён

[body]
max_health   = 90.0               # прочность собранного юнита
radius       = 0.32
vision_range = 9.0

[movement]
speed      = 4.0
turn_speed = 240.0

[assembly]
cost_metal   = 60.0               # он же объём работы: время = стоимость / мощность
frame_health = 120.0              # прочность каркаса — другая величина, и названа иначе
```

**Инструменты** лежат рядом с носителем (`resources/units/player/<id>/`, `resources/buildings/<id>/`), как `tools` в PA; в `resources/tools/` остаются только общие основы вроде `base_weapon`. Ствол и строительная рука — самостоятельные определения со своей дальностью, мощностью и прожорливостью. Носитель ссылается на инструмент по идентификатору. Стволы наследуют `base_weapon` (числа совпадают с умолчаниями `WeaponDefinition`); конкретный файл перекрывает только отличия. Прочность, энергия, металл и урон — 1:1 с PA; скорость и дальность пересчитываются под клетку мира.

**Теги** объявляются единым перечнем в `resources/content/tags.toml` и нигде больше. Тег, не объявленный там, — ошибка сборки, а не молча заведённая новая категория. Из тегов выводятся следствия, которые раньше были константами в коде: род при выделении определяется тегом `structure`.

**Наследование TOML** — ключ `base` на корне файла и в секциях: значения основы подставляются снизу, ключи текущего файла перекрывают их сверху. Путь пишется от `resources/`: `base = "/units/base_unit.toml"`. Подвижные берут `base_unit`, постройки — `base_building`; противник дополнительно наследует `base_enemy`; стволы — `base_weapon`. В значении отдельного поля можно указать путь к другому файлу — берётся одноимённое свойство (сначала из той же секции). Справочник констант — `resources/content/units.vars.toml`; в пути обязательно имя свойства: `vision_range = "/content/units.vars.toml/vision_range"`. В base-файлах — шаблон (секции, умолчания полей); в vars — общие скаляры. Все файлы загружаются до разрешения ссылок; кольцо зависимостей — ошибка со списком участников. Определение с `abstract = true` служит только основой и в каталог не попадает. Ключ `extends` больше не поддерживается.

**Приказы** — секция `[orders]` с массивами `allow` и `deny`. После слияния `base` принятый список файла: `allow` минус `deny`. К исполнению идёт пересечение с фактическими возможностями. `deny` — явный запрет: приказ не принимается и в панели не показывается. Отсутствие в `allow` без `deny` при наличии умения — мягкий статус со звёздочкой (неопределённость на время проверки полноты списка).

Форма постройки задаётся **матрицей строк** (`rows`), поэтому формы могут быть не только прямоугольными. Там же, в секции `[footprint]`, живёт требование к месту: `requires_metal_spot = true` означает «ставится только на точку метала». Признак относится к месту, а не к постройке, поэтому лежит рядом с формой — и то, и другое отвечает на вопрос «куда это встанет».

Списка «кому эта постройка доступна» у постройки нет намеренно: на вопрос отвечает строительная панель строителя, и держать тот же факт с двух сторон значило бы однажды их рассогласовать.

Каталог нужен по трём причинам, и первая — главная:

1. **Документы носят строковый `DefinitionId`, а не ссылку** — так они переживут сохранение. Кто-то должен превращать этот идентификатор обратно в определение, иначе запись «поставлен `factory` в клетке (5,2)» нечем восстановить.
2. Надо уметь **найти определение по id** — по нему строительная панель превращает ячейку `build = "turret"` в кнопку со стоимостью.
3. Чтение один раз на старте, пути к файлам не размазаны по коду.

Каталог — **только чтение**. Он ничего не создаёт и не знает о живых сущностях: создание в `Spawner`, живые экземпляры в `EntityStore`. Сам он и не собирает: разбор, наследование и проверки — в `ContentCompiler`.

#### Сборка содержимого — ContentCompiler

Сборка — не чтение файлов подряд. У неё четыре обязанности, и ни одна не сводится к одному файлу:

1. **Развернуть наследование TOML** — `base`, ссылки на файлы в полях и `*.vars.toml` материализует `TomlResolver` до типизированного чтения.
2. **Разрешить ссылки** — строки `tools = [...]`, `tags = [...]`, `buildbar = "..."` однократно превратить в объекты и маски, чтобы игра дальше по словарю не ходила.
3. **Проверить связность** — ячейка панели, ссылающаяся в пустоту, раньше обнаруживалась при попытке нарисовать кнопку, то есть могла не обнаружиться вовсе. Теперь это ошибка на первом кадре, с именем файла и секции.
4. **Вывести следствия** — род выделения, ствол, рабочие инструменты и наборы приказов вычисляются один раз и ложатся полями.

Разбор строгий: `TomlDocument` помечает израсходованные ключи, и всё, до чего никто не добрался, объявляется ошибкой. Без этого опечатка в имени ключа молча оборачивается умолчанием — юнит с прочностью не той, что написана в файле.

Сборка идёт **в памяти**. Генерация `.tres` из `.toml` дала бы два представления одних данных, и какое из них главное, пришлось бы решать соглашением, которое рано или поздно нарушат.

#### Почему не ресурсы Godot

Определения правят руками и часто, а правит их по большей части агент. В `.tres` содержательные числа перемешаны со служебными: `load_steps`, `uid`, ссылки вида `ExtResource("2_scene")`. Их приходится поддерживать вручную, и они уже успели разъехаться — часть файлов проекта носила `uid` без `load_steps`, часть наоборот. Комментариев `.tres` не поддерживает вовсе, а в определении важно бывает записать, почему число именно такое.

Цена решения: перемещение файла Godot больше не исправляет ссылку сам (её проверяет компилятор при запуске), а `.toml` не является импортируемым ресурсом и попадает в экспортируемый пакет только по явному фильтру.

### 5.3 Документы

Структура (не класс), имя в прошедшем времени, внутри — только данные и стабильные идентификаторы, **никогда** ссылки на ноды.

```csharp
public interface IEventRecord
{
    int SequenceId { get; set; }   // проставляет сам поток при дозаписи
}

[TransientEvent]                    // живёт один кадр
public struct BlueprintPlaced : IEventRecord
{
    public int SequenceId { get; set; }
    public int EntityId;
    public string DefId;            // ключ справочника
    public Vector2I Cell;
}
```

Структура, а не класс — потому что документов десятки в секунду, а значимый тип не грузит сборщик мусора.

**Приказы документами не являются.** Документ — уже свершившийся факт, его нельзя отклонить или отменить. Приказ (`Order`) — это намерение, он живёт отдельно, в очереди юнита.

Транзиентность — **атрибут**, а не интерфейс-маркер: время жизни это метаданные о записи, а не её разновидность.

### 5.4 Журнал — EventStore и EventStream

```csharp
public sealed class EventStream<T> : IEventStream where T : IEventRecord
{
    public event Action<T> Appended;              // сюда подписываются проекции
    public IReadOnlyList<T> Records => _records;   // системам, читающим пачкой за кадр

    public bool IsTransient { get; } =
        Attribute.IsDefined(typeof(T), typeof(TransientEventAttribute));

    public void Add(T record)
    {
        record.SequenceId = ++_lastSequenceId;
        _records.Add(record);
        Appended?.Invoke(record);
    }
}
```

У потока две разные роли, и путать их не надо: `Appended` — подписка (так работают проекции), `Records` — список за кадр (для разбора пачкой).

Метод дозаписи называется `Append`, а не `Publish`: журнал — append-only лог, и имя должно учить структуре данных.

```csharp
Events.Append(new ResourceSpent { Kind = ResourceKind.Ore, Amount = use });
Events.Stream<ResourceSpent>().Appended += OnSpent;
```

**Сегодня это шина в пределах кадра, а не долговременный лог:** все документы проекта помечены `[TransientEvent]`, журнал вычищается каждый кадр и историю не хранит. Долговременный лог понадобится для сохранений — тогда часть потоков перестанет быть транзиентной (см. раздел 6).

### 5.5 Проекции

Проекция отвечает на вопрос «сколько сейчас», документ — на вопрос «что случилось».

**Главное правило: обновляться дельтой в момент дозаписи, а не пересчётом из истории.** Два следствия:

1. Журнал можно чистить и усекать — проекция самодостаточна.
2. Стоимость обновления не растёт вместе с числом сущностей.

Именно на этом обжёгся прошлый прототип (CircleSlugs): там регистр суммировал всех живых врагов заново на каждый спавн и каждую смерть.

```csharp
public abstract class Projection
{
    public event Action Changed;                      // отсюда обновляется представление
    protected void NotifyChanged() => Changed?.Invoke();
    public abstract void Subscribe(EventStore events); // зовётся один раз при старте
}

public sealed class StockpileProjection : Projection
{
    private readonly Dictionary<ResourceKind, float> _amount = new();

    public float Get(ResourceKind kind) => _amount.GetValueOrDefault(kind);

    public override void Subscribe(EventStore events)
    {
        events.Stream<ResourceGained>().Appended += r => { Apply(r.Kind, +r.Amount); };
        events.Stream<ResourceSpent>().Appended   += r => { Apply(r.Kind, -r.Amount); };
    }
}
```

**У проекции нет и не должно быть методов «добавить» или «списать».** Чтобы запас изменился, публикуй документ — тогда у каждого изменения есть след в журнале, и правило не обходится втихую.

### 5.6 Системы, планировщик и фазы

Система — нода: её добавляют в сцену и настраивают в инспекторе. Порядок исполнения задаётся полем, а не порядком нод в дереве.

```csharp
public partial class GameSystem : Node
{
    [Export] public Phase Phase = Phase.Simulate;
    [Export] public int StepOrder;          // чем меньше, тем раньше внутри фазы
    [Export] public UpdateCycle UpdateCycle = UpdateCycle.PhysicsProcess;

    // Менеджера берём из предков, а не из статической ссылки: система принадлежит
    // тому корню, под которым висит, и на сносе сессии это единственный надёжный путь
    protected GameManager GM { get; private set; }

    public override void _EnterTree() { GM = Ancestor<GameManager>() ?? GameManager.I; }
    public override void _ExitTree() => GM?.Scheduler.Remove(this);

    public override void _Ready()
    {
        GM?.Scheduler.Add(this);
        OnRegister();

        // Систему, добавленную после сборки сессии, связываем сразу: общей точки
        // «все зарегистрированы» она уже опоздала застать
        if (GM is { SystemsLinked: true }) Link();
    }

    protected virtual void OnRegister() { }   // фаза 1: настройка себя
    protected virtual void OnLink() { }       // фаза 2: связывание с соседями
    public virtual void Step(double dt) { }
}
```

Фазы: `Input` → `Simulate` → `React` → `Cleanup`. Цикл обновления (`UpdateCycle`) выбирает, из какого колбэка корня система попадёт в прогон: `PhysicsProcess` (по умолчанию, симуляция) или `Process` (представление). Это разные циклы Godot в одном потоке, не отдельные потоки исполнения. `Index.Sweep` и очистка транзиентных документов остаются только в физическом цикле.

#### Инициализация в две фазы

Порядок `_Ready` определяется расстановкой узлов в сцене, поэтому в `OnRegister` система не вправе рассчитывать, что соседи уже существуют. Второй хук `OnLink` вызывает композиционный корень из собственного `_Ready`, а он приходит после `_Ready` всех дочерних узлов — состав систем к этому моменту заведомо полон.

Отсюда главное следствие: **взаимные ссылки работают без разбора графа зависимостей.** Если система A нуждается в B, а B в A, то состояния, в котором обе зависимости «инициализированы», не существует ни при каком порядке вызовов; поиск такого порядка бесплоден по существу. Единственное разрешимое условие — «все зарегистрированы», и Godot даёт этот момент даром, уведомлением `_Ready` родительского узла. Пул с графом зависимостей, обратными вызовами по готовности и таймаутом решал бы ту же задачу дороже и позже: состав систем задан сценой и известен заранее, поэтому отсутствие зависимости есть ошибка конфигурации, которую следует обнаруживать сразу, а не по истечении срока ожидания.

**Чего во второй фазе ещё нет: населённого мира.** Стартовые сущности создаёт `Session`, и его `_Ready` приходит позже нашего. Работа, которой нужен готовый мир, по-прежнему откладывается до первого кадра — так поступает `MetalSpotSystem`, и не по недосмотру: точки метала нельзя расставлять раньше базы, иначе они встанут на её клетки.

Полноценный пул понадобится тогда, когда состав систем перестанет быть известным на момент создания сессии — при подгружаемых модификациях или содержимом, приходящем по сети. Двухфазная схема при этом станет его частным случаем.

#### Поиск системы по типу

```csharp
var command = GM.System<CommandSystem>();   // null, если системы в сцене нет
```

Раньше каждая система, нужная другим, получала собственное свойство в `GameManager` (`Command`, и далее по одному на каждую), а сама прописывала себя туда в `OnRegister`. С ростом числа систем это не масштабируется, поэтому реестр по типу заведён в `Scheduler`: он и без того единственный держатель состава систем, а параллельный контейнер неизбежно разошёлся бы с ним при добавлении или удалении. Ключом служит как объявленный тип, так и любой базовый, по которому систему однажды спросили. Две системы одного типа делают ответ произвольным, поэтому такая сборка сцены встречается предупреждением.

Текущий порядок в `Session.tscn`: `CursorSystem` (Input, графический цикл, раньше команд) → `CommandSystem` (Input, графический цикл) → `PlayerAiSystem` → `EnemyAiSystem` → `OrderSystem` → `EconomySystem` → `MetalSpotSystem` → `PressureSystem` → `WeaponSystem` → `ProjectileSystem` → `DamageSystem` (React). Симуляционные системы по умолчанию в физическом цикле. Одна система участвует ровно в одном `UpdateCycle`: одновременно в физическом и графическом циклах ей быть нельзя.

Порядок внутри фазы не декоративен:

- **Мозги раньше исполнителя** — приказ, поставленный в этом кадре, в этом же кадре и отрабатывается, а не через один.
- `OrderSystem` раньше `EconomySystem` — сначала исполнители подключаются к узлам работы, потом узлы работают.
- Движение раньше `WeaponSystem` — стреляют по той позиции, куда все уже сдвинулись за этот кадр.
- `DamageSystem` в отдельной фазе `React` — см. 5.12.

### 5.7 Сущности, Spawner, EntityStore и Index

- **Видимое или физическое** — нода (`Node2D`, при необходимости `CharacterBody2D`, `Area2D`).
- **Данные сущности** — обычные C#-объекты, которыми владеет нода. Не плодим ноды на каждую характеристику.
- У сущности стабильный `EntityId`.

Создание сущностей — **только через `Spawner`**. Он владеет обрядом: выдать id, поднять сцену, инициализировать, занять клетки, положить в свой слой площадки, в `EntityStore` и в `Index`. Вынесено потому, что раньше эти шаги дословно повторялись в пяти местах, и правило «кто занимает сетку и кто попадает в реестр» расползалось по системам. Снятие с сетки и из `EntityStore` тоже живёт здесь: подписка на выбытие из индекса чистит реестры по снимку, сделанному при регистрации. `OnDestroyed` сущности только выводит ноду из игры (`Detach`, `QueueFree` и т.п.) — реестры руками не трогает.

```csharp
var blueprint = GM.Spawn.SpawnBlueprint(BlueprintScene, def, origin);
GM.Spawn.SpawnBuilding(def, cell);
GM.Spawn.SpawnUnit(scene, position);
GM.Spawn.SpawnOre(scene, cell);
```

Это **не** метод каталога: каталог только читает, а создание трогает сетку, реестр и дерево сцены. Смешаешь — справочник потащит за собой полмира.

#### Index — как системы находят, с кем работать

Системе почти никогда не нужен один объект: ей нужны все вооружённые, все участники экономики, все каркасы. Раньше этот вопрос задавали движку через **группы нод**, и способ оказался плохим по трём причинам сразу: ключом была строка (её не проверяет компилятор и не задевает переименование), ответом — нетипизированный `Array<Node>` (каждая система приводила и отсеивала его сама), а порядок брался из дерева сцены и плыл при удалениях.

Ключ разреза — **тип-признак, обычно интерфейс**. Отсюда даром достаётся множественное членство: сущность попадает в столько разрезов, сколько интерфейсов реализует, — юнит разом и цель, и стрелок, и участник экономики.

```csharp
foreach (var armed in GM.Index.All<IArmed>())            // разрез по признаку
foreach (var actor in GM.Index.All<IEconomyActor>())

GM.Index.All<Blueprint>()                                 // тот же разрез, сужённый фильтром
    .Where(blueprint => blueprint.NeedsWork)
    .Nearest(from, blueprint => blueprint.GlobalPosition);

GM.Targets[Faction.Hostile]                               // постоянный разрез по ключу
```

**Заводят что-либо только два вызова: `All<T>()` и `SliceBy(...)`.** Первый при первом же спросе набирает список по признаку, второй регистрирует разрез по ключу; оба потом живут до конца сессии. `Where` не заводит ничего — он возвращает ту же структуру, указывающую на тот же список, плюс делегат. По сути это `if … continue` в теле обхода, вынесенное на место вызова, и нужен он затем, чтобы сузить разрез для `Nearest`, `First` и `Count`, которые владеют циклом сами. Пишете свой `foreach` — пишите обычное условие: понятнее и без вызова делегата на каждом шаге.

Что чем закрывать:

| Природа условия | Чем | Пример |
|---|---|---|
| Тип сущности | выбор разреза `All<T>()` | «только постройки» против «всё, что чинится» |
| Устойчивый ключ, спросов много за кадр | `SliceBy` | цели по стороне |
| Занятость клетки | не индекс, а `WorldGrid` | что под курсором |
| Зависит от спрашивающего или мигает чаще кадра | `Where` | расстояние, `NeedsWork` |

**Разрез — окно в живой список, а не копия.** Перебор идёт по номеру и на ходу отбрасывает мёртвых, поэтому системе не нужно ни приводить тип, ни проверять живость: обход отдаёт только то, с чем можно работать. Своей памяти разрез не занимает.

**Проверка живости написана ровно в одном месте** (`Index.IsLive`): нода жива, пока цела и не помечена `QueueFree`, всё прочее — пока его не сняли явно. Из этого следует главное свойство: **ноду нельзя забыть снять с учёта.** Раньше каждая сущность перечисляла свои группы дважды — при рождении и при гибели, — и списки эти жили в семи файлах.

**Состав множества меняется на границе кадра.** Добавления и снятия копятся, а применяются в `Index.Sweep()` — его зовёт `GameManager` после всех систем. Иначе рождённое посреди кадра попадало бы в одни обходы и не попадало в другие, в зависимости от порядка систем. Побочная выгода: список не меняется под ногами у системы, которая по нему идёт.

**Постоянный разрез по ключу** (`SliceBy`) нужен там, где спросов за кадр много: в `Targets` смотрит каждый ствол на каждом выстреле и каждый снаряд на каждом кадре полёта. Пересобирается он лениво и не чаще раза за кадр, поэтому ключ обязан быть таким, который посреди кадра не меняется. Для мигающих значений разрез не годится — там фильтр.

Индекс **ничего не знает про сущности**: складывать в него можно любой объект, не только ноду. Разрезы одинаково нужны и живому миру, и обычным данным.

### 5.8 Места работы — IWorkSite, план и каркас

Стройка проходит две стадии, и сущности у них разные.

**План (`BuildPlan`) — намерение, а не строение.** Он появляется в мире по щелчку игрока, ходьбе не мешает, прочности не имеет и обстрелу не подлежит: атаковать в нём нечего. Единственное, на что он влияет, — на постановку следующих планов и строений, поэтому его форму читает `Placement`, а карта препятствий о нём не знает вовсе. Из этого следует главное игровое изменение: застройка стала следствием присутствия. Раньше каркас возникал в любой точке карты мгновенно, и стену перед наступающим противником можно было поставить, не имея там ни одного юнита. Гибель назначенного исполнителя план не снимает — за него может взяться другой; отказ игрока от приказа (замена очереди без Shift) снимает те планы из брошенного остатка, на которые больше никто не нацелен.

**Каркас (`Blueprint`) — материальный объект.** Он появляется на месте плана тогда, когда до него дошёл исполнитель, занимает место, ломается и тянет метал. План при этом уходит из мира, а у приказа **переезжает цель**: план объявляет, что сменился каркасом, и нацеленный на него приказ переводит цель на преемника сам. Если место к приходу исполнителя оказалось занято (план его не держал), план тихо отменяется без объявления, и очередь идёт дальше.

**Почему объявление, а не поиск.** Приказ на каркас прежде вписывался в очередь следом за приказом на план, и чтобы найти очереди, где тот значится, план перебирал все ветки приказов через индекс. Перебор этот работал не всегда: индекс впускает новых членов на границе кадра, а ветка заводится щелчком в графическом цикле, — поэтому у исполнителя, которому не пришлось никуда идти, приказ на каркас молча терялся, и первая постройка партии оставалась стоять каркасом. Объявление `IWorkSite.Superseded` эту зависимость снимает целиком: список подписчиков и есть та обратная связь «место работы — приказы», которой не хватало. Заодно уходит и вставка в середину списка — приказ остаётся тем же объектом на прежнем месте во всех ветках, где он значится.

**В очереди на постройку поэтому один шаг, а не два.** План и каркас суть две стадии одной постройки, а не две разные задачи, и шаг этот живёт от разметки до готового строения.

Общее у них — признак `IWorkSite`: место в мире, признак незаконченности и объявление о собственной смене. Больше ничего общего и нет, потому что требуют они разного: **каркас требует мощности**, план — **присутствия**. Поэтому подключение мощности осталось у `WorkNode` и в общий признак не поднято.

Форма `WorkNode` — для всякой работы, которую несколько исполнителей делают сообща: каждый сообщает свою мощность, узел складывает их в суммарный поток и сам двигает ресурсы. Наследник сейчас один — каркас (`Blueprint`), тянущий метал из хранилища по суммарной мощности подключённых строителей.

Абстракция шире единственного наследника намеренно. Вторым был `OreDeposit`: пока метал добывали вручную, месторождение и каркас действительно были одним и тем же с точки зрения механики — оба принимали подключения и оба двигали ресурс, только в разные стороны. Добыча стала пассивной (см. 5.9), месторождение ушло, а форма осталась и понадобится любому следующему занятию с общей мощностью.

```csharp
public abstract partial class WorkNode : Node2D, IEconomyActor
{
    private readonly Dictionary<int, float> _connections = new();  // id исполнителя -> мощность

    public float TotalPower { get; private set; }   // пересчитывается дельтой
    public abstract bool NeedsWork { get; }         // по этому признаку боты ищут работу

    public void AttachWorker(int workerId, float power);
    public void DetachWorker(int workerId);
    public abstract void Declare(EconomyLedger ledger);      // заявить потоки
    public abstract void Run(double dt, float efficiency);   // отработать тик
    protected void ReleaseWorkers();                // узел уходит — отпускает исполнителей
}
```

Ключевое: **исполнитель только сообщает свою мощность, ресурсы двигает узел** — одним запросом за тик, а не обходом всех подключённых. Локальный реестр подключений живёт внутри самого узла.

Не хватает ресурсов — работа **замедляется пропорционально**, а не встаёт колом. Раньше долю считал сам узел, теперь она общая на всю базу и приходит извне (см. 5.9): производительность не может быть личным делом одного каркаса, когда поток один на всех.

### 5.9 Экономика: два ресурса и производительность базы

Ресурса ровно два, и роли у них разные. **Метал** — материал: из него состоят постройки, он копится и тратится. **Энергия** — не материал, а пропускная способность: сама она ничего не образует, но без неё метал не потратить. Модель повторяет экономику PA.

**Экономика потоковая.** Стоимость не списывается при постановке — она размазана по всему времени стройки. Мощность строителя измеряется металом в секунду, поэтому объём работы у постройки равен её стоимости в метале: `TotalWork == CostMetal`.

**Энергоцены у постройки нет — она у инструмента.** Энергию жжёт сварка, а не бетон, поэтому расход задаётся определением инструмента (`WorkToolDefinition.EnergyPerPower`), а узел работы копит сумму подключённых инструментов в `TotalEnergy` — той же дельтой, что и `TotalPower`. Одно и то же здание обходится дороже, если его варит прожорливый коммандер, и дешевле, если экономный фабрикатор. Побочная выгода: у постройки на один параметр меньше, и его не надо согласовывать со стоимостью.

**Расчёт производительности — вот он целиком** (`EconomyLedger.Resolve`):

```
доступно(вид)  = запас + доход · dt
спрос(вид)     = Σ заявок потребителей · dt          ← заявка НЕ умножается на КПД
КПД(вид)       = спрос <= 0 ? 1 : clamp(доступно / спрос, 0, 1)

ТЕМП РАБОТЫ = min( КПД метала, КПД энергии )         ← он же «производительность» в HUD
```

Дальше — важное правило, которое легко потерять: **расход двух ресурсов ужимается по-разному.**

| Ресурс | Чем ужимается | Почему |
|---|---|---|
| Метал | темпом работы `min(…)` | построили меньше — меньше и заплатили; полная цена не меняется |
| Энергия | только своим КПД | мощность оплачена целиком, даже если стройка еле ползёт из-за метала; лишнее сгорает |

Отсюда следует главное правило игры: **просадку по энергии лечат генераторами.** Потребители сами себя не подожмут — если энергии в обрез, а метала нет, энергия всё равно тратится под ноль.

И встречное следствие: актор применяет только ту долю, которая его касается. Экстрактор и синтезатор упираются в `КПД энергии` — метал они производят, и его нехватка их не тормозит. Каркас упирается в обе.

Три свойства модели, ради которых всё и затевалось:

1. **Цена не меняется, меняется скорость.** При 50% две стройки идут ровно так же быстро, как одна при 100%. Никаких очередей, отключений и приоритетов.
2. **Просадка общая.** Производительность одна на всю базу, поэтому нехватка энергии тормозит и добычу, и стройку — а не выбирает жертву.
3. **Запас — демпфер.** Пока в хранилище что-то есть, короткие всплески спроса не роняют производительность. Пустое хранилище — просадка ровно во столько раз, во сколько не хватает дохода.

**Кадр обязательно идёт в два прохода** (`EconomySystem`): сначала все участники объявляют потоки (`Declare`), потом узнают производительность и работают (`Run`). Иначе получаются качели: отработали вполсилы → спрос упал → в следующем кадре КПД 100% → снова полная нагрузка → снова просадка. По той же причине заявка всегда номинальная: ужимать её на КПД — значит решать уравнение с самим собой.

**В HUD показывается спрос, а не фактический расход.** Ужатый расход всегда выглядит почти сведённым с доходом, и по нему не понять, чего и насколько не хватает. По спросу видно сразу: столько-то генераторов недостаёт.

Одно сознательное упрощение: **доход заявляется по номиналу.** Экстрактор объявляет выработку так, будто энергии хватит, хотя реально она просядет вместе с производительностью. Иначе получилось бы уравнение с самим собой — «сколько будет дохода при той производительности, которую мы как раз вычисляем». Так же поступает и PA, погрешность в пользу игрока и живёт один кадр.

Кто участвует в экономике: коммандер (собственный доход — без него первый генератор и первый экстрактор не на что строить), генераторы, экстракторы (жгут энергию и дают метал), каркасы, синтезатор метала (то же самое по невыгодному курсу — сброс излишков энергии). Состав задан одним интерфейсом `IEconomyActor`: реализовал — значит участвуешь, отдельного списка нет и разъехаться нечему.

#### Метал — позиционный ресурс

**Добыча пассивна и привязана к месту.** Точки метала расставлены при создании мира, вечны и одинаковы; экстрактор ставится на точку и качает, пока стоит. Отсюда единственный способ поднять доход — занять новую точку, то есть выйти за прикрытый периметр.

Так было не всегда, и смена модели стоит объяснения. Раньше метал добывали копатели: месторождение было узлом работы с конечным запасом, к нему подключались буром, а выработанные слоты восстанавливались в кольце вокруг базы. Схема отменена по двум причинам. Первая: восстанавливаемая руда у базы делает пространство бесплатным, и вопроса «куда расширяться» не возникает вовсе. Вторая: конечное месторождение требует переставлять копателей вручную, а это расход внимания игрока, ничего не решающий, — при том что внимание в этой игре главный дефицит.

Механика экстрактора и синтезатора одна и та же (`UnitClass.Factory`): энергия в метал. Различаются они курсом и требованием к месту, и обе величины лежат в `.toml`, а не в коде.

**Ёмкость хранилища** складывается из базовой константы и вклада построек, меняется дельтой по документам `BuildingSpawned` и `EntityDestroyed`. Сверх потолка приход пропадает — лишняя энергия сгорает, как в PA.

Здесь же тонкость про `BuildingSpawned`: он публикуется фабрикой сущностей, а не каркасом. `ConstructionCompleted` говорит «стройка завершена», а ёмкость зависит от «постройка есть» — стартовая база появляется вообще без стройки.

### 5.10 Поле зрения, ремонт и выбор работы

**Поле зрения есть у всего** — у зданий, каркасов, ботов, коммандера и врагов, единым интерфейсом `IVision` с радиусом из справочника. Тумана войны в игре нет, и на видимость радиус пока не влияет; заведён он потому, что уже работает как **рабочая зона**: фабрикатор чинит то, что видит, башня-сборщик обслуживает свой круг. Разносить «что вижу» и «докуда дотягиваюсь» по двум разным параметрам задним числом было бы дороже, чем сразу назвать это одним.

**Ремонт — это стройка уже стоящей сущности.** Отдельной ремонтной мощности нет: чинит та же строительная рука, что и строит, и жрёт столько же энергии — как build power в PA. Заявка в экономику у ремонта и стройки буквально одна и та же.

**Курс выводится из цены, а не задаётся руками:** `MaxHealth / CostMetal` прочности за метал. Отсюда два следствия, ради которых так и сделано: починить с нуля стоит ровно столько же, сколько построить, и занимает столько же времени. Балансировать ремонт отдельно не нужно — он балансируется вместе с ценой. Нет цены — нет и курса: `HealthPerMetal == 0` означает «ремонту не подлежит».

Чинить можно и постройки, и юнитов — обе стороны реализуют `IRepairable`. Прочность и цена теперь лежат в одном определении, поэтому курс считает оно само; раньше юнит описывался двумя файлами, и курс приходилось складывать из половинок. У коммандера секции `[assembly]` нет — значит нет цены, нет курса, и чинить его нечем. Ему это ни к чему: урон он копит, но не гибнет.

Берётся ли строитель за юнитов, а не только за постройки, — свойство инструмента (`repairs_units`), а не носителя: ремонтник поля боя и строитель базы работают одной и той же рукой.

**Берётся ли строитель за юнитов — отдельный переключатель** (`CanRepairUnits`). Это вопрос не умения, а назначения: ремонтник поля боя и строитель базы — разные роли при одном и том же инструменте.

Ремонтирует не постройка, а тот, у кого инструмент: `Building` не может стать `WorkNode` (базовый класс уже занят), да и незачем. Отсюда простое правило: **стройку узел тянет сам, ремонт делает исполнитель.** Вся механика ремонта живёт в одном месте (`Repair`), а зовут её одинаково и подвижный фабрикатор, и неподвижная башня.

**Что исполнитель берёт на себя сам** (`PlayerAiSystem`), а что делает только по приказу:

- **стройку** сам берёт лишь неподвижный — башня-сборщик, — и только в пределах манипулятора: бежать ей некуда, она обслуживает то, что оказалось под рукой. Подвижный строит по приказу, и это не ограничение: постановка плана и есть приказ строить, отдаваемый тем же щелчком. Прежде фабрикатор без дела убегал строить через полкарты, и отряд строителей растекался по ней сразу после того, как игрок его собрал;
- **ремонт** сам берёт чистый ремонтник, чей инструмент строить не умеет (`stitch`). Роль выводится из снаряжения, а не задаётся признаком: рука, которой нельзя построить, заведена ровно затем, чтобы чинить;
- **огонь** по цели в пределах внимания берут все вооружённые: оборона не ждёт указаний.

**Всё самостоятельное ограничено радиусом внимания вокруг якоря** (`IWorker.Anchor`) — точки последнего приказа игрока, а не текущего положения. Поиск от собственного положения ползёт: юнит отошёл к цели, от новой позиции нашёл следующую, — и через минуту отряд, поставленный держать рубеж, оказывается на другом конце карты. Приказ, выданный системой, помечается поводком (`Order.Leashed`): цель, ушедшая за предел внимания, его обрывает. Прямое указание игрока поводка не имеет и ведёт юнита сколь угодно далеко.

Радиус внимания равен радиусу обзора и отдельным числом не задаётся: внимание есть готовность отреагировать на то, что сущность видит.

- **Сопровождение — это отсутствие работы, а не работа.** Бот с приказом `Follow` считается свободным и бросает его, как только появится дело. Иначе боты, однажды пошедшие за коммандером, больше никогда бы не строили.
- **Сопровождение включает помощь и прикрытие.** Строитель, приставленный к строителю, берётся за то же дело, что и ведущий; если ведущий сам идёт по `Follow`, разбор идёт дальше по цепочке, пока не найдётся стройка или ремонт, — искать «исходного» строителя снаружи не нужно. Вооружённый отходит к противнику, появившемуся в поле внимания ведущего, и возвращается сам. Ни то ни другое в очередь не попадает: это поведение внутри приказа сопровождения, а не приказ. Попади оно в очередь — его пришлось бы оттуда вынимать, а до тех пор помощник считался бы занятым и сопровождение потерял.
- **Follow с хвостом очереди завершается.** Одиночный `Follow` живёт, пока жив ведущий. Если за ним уже стоит следующий приказ, сопровождение снимается после рандеву или когда ведущий без дела — но не пока идёт помощь стройке или прикрытие.

**Башня-сборщик** (`Assembler`) — тот же фабрикатор, только здание, и обслуживается той же системой: и он, и она реализуют `IWorker`, поэтому задачи им раздаются одним обходом. Различаются они пределами поиска, и те выводятся из определения — неподвижный ищет и стройку, и повреждённое в пределах манипулятора. Отдельная `AssemblerSystem` убрана: она свелась к трём строкам и повторяла решение, которое принимала сама башня, то есть держала одно правило в двух слоях. В стройке она участвует как обычный исполнитель — подключается к каркасу мощностью, и дальше каркас сам заявляет спрос. А ремонт делает сама, поэтому в экономике участвует ещё и напрямую.

### 5.11 Приказы: единая форма для всего, что действует

**Очередь приказов есть у всего, что может действовать** — у ботов, коммандера, врагов, турелей и башен-сборщиков. Слово «юнит» здесь широкое: **постройка — тоже юнит**, разница между ней и ботом не в наличии очереди, а в том, что в её наборе.

```csharp
public interface IOrderable
{
    OrderSet AllowedOrders { get; }   // принято к исполнению
    OrderSet SoftOrders { get; }      // умеет, но в [orders] не разрешено
    OrderQueue Orders { get; }
    void RunOrder(Order order, double dt);
    void OnIdle(double dt);
}
```

**Три исхода для приказа.** Фактическая исполнимость — из класса и снабжения (`ExecutableOrders`). `allow` минус `deny` даёт объявленное; пересечение с исполнимым — `AcceptedOrders` (очередь принимает). Исполнимое, но не попавшее ни в allow, ни в deny — `SoftOrders` (панель со звёздочкой, очередь не принимает). Попавшее в `deny` скрыто полностью: ни очередь, ни панель.

**Снос (`OrderKind.Delete`).** Del выдаёт выделенным приказ сноса с заменой цепочки (как ПКМ без Shift), но только тем, у кого снос в `AllowedOrders`. Исполнение публикует `DamageDealt` на себя, гибель разбирает `DamageSystem` в React. У коммандера и крепости снос снят через `deny`; у остальных юнитов и построек игрока он разрешён.

**Мозг отделён от исполнителя.** Приказы раздают системы выдачи задач — `PlayerAiSystem` всему, что работает на стороне игрока, включая неподвижные башни-сборщики, `EnemyAiSystem` противнику, `CommandSystem` по воле игрока. Исполняет приказ сама сущность, а зовёт её единственная `OrderSystem`, обходя разрез `All<IOrderable>()`. Отсюда важное следствие: **юнит противника отличается от союзного своим мозгом, а не своим кодом движения.** С отдельным классом `Enemy` это правило держалось на честном слове: код движения был выписан дважды. Теперь класс один, а сторона хранится полем `Faction`.

Мозг ставит приказ только свободному: приказ игрока важнее самодеятельности и не должен перебиваться каждым кадром. Освободится юнит сам — отработанный приказ снимет с очереди `OrderSystem`.

**Невыполнимость — свойство приказа, а не исполнителя**, поэтому проверка живёт в `Order.IsValid()` и одна на всех: цель пала, каркас достроен, повреждённое починено. `OrderSystem` снимает такие приказы с головы очереди, и до `RunOrder` приказ доходит заведомо годным — проверять живость цели в каждой ветке движения не нужно.

**Ставим всё или ничего.** Если хоть один приказ цепочки недопустим, очередь не меняется вовсе: иначе «дойти и починить» превратилось бы в «дойти», и юнит молча встал бы посреди карты.

**Очередь — сущность индекса, а не поле юнита** (`OrderList`). Список приказов лежит в индексе и держится своими подписчиками: не осталось живых — очередь уходит сама. Юниту принадлежит только то, что у каждого своё, — место в этом списке (`OrderQueue`), и хранится оно **ссылкой на приказ, а не номером**: в середину бывает вставка, и номер после неё означал бы другой приказ.

Пока список принадлежал юниту, владельцем времени жизни очереди оказывался последний живой участник, а взять на неё ссылку можно было только у него же. Отсюда три вещи, которых не хватало: подписать на работающую очередь нового исполнителя было нечем, перечислить идущие в игре задачи негде, выписать очередь в документ невозможно по той же причине.

**Отряд работает по одной очереди, расходясь указателями:** кто-то уже взялся за второй приказ, пока другой заканчивает первый. Поэтому приказ снимается из списка не тогда, когда его исполнил первый, а когда мимо него прошли все — и когда сверху не осталось никого, кто до него ещё дойдёт.

**Подписчик ветки — либо курсор исполнителя, либо другая ветка** (`IOrderFollower`). Список подписчиков поэтому один, а не два: ветка отвечает за своих участников ровно так же, как курсор отвечает за себя, и различать их снаружи незачем. Пристегнуть ветку значит подписать её — ссылка вперёд и подписка назад суть одно отношение, записанное с двух сторон. Три вопроса, которые ветке задают, — живость, ожидание приказа, принадлежность выделению — курсор решает за одного себя, а ветка обходом собственных подписчиков, то есть вверх по цепочке. Подписчиком служит именно курсор, а не сущность: все три вопроса суть свойства указателя, и `OrderList` о юнитах не знает вовсе.

Состояние исполнения — кому приказ роздан и кто уже на месте — записано в самом приказе. Отсюда два следствия, ради которых это и сделано. Первое: подошедший вторым видит, что работа уже начата, и включается в неё. Второе: **приказ движения дожидается отставших** — дошедший первым стоит, пока не соберутся остальные, иначе отряд, посланный в две точки подряд, прибывал бы во вторую по частям. Погибшие из состава выбывают, поэтому одна потеря отряд не замораживает; неподвижные не ждутся вовсе, потому что дойти не могут никогда.

**Ветки сцепляются.** Приказ по Shift достаётся тем, кто занят разным: у одного своя очередь, у второго своя, третий свободен. Дописать его каждому по отдельности значило бы размножить одно намерение по спискам — а оно одно, и вставка в него потом должна быть одна. Поэтому дописанное заводится отдельной веткой, а к ней **пристёгиваются хвосты** тех очередей, что её получили: каждый доделывает своё и переходит в общую.

**Подписка переезжает вместе с указателем:** курсор всегда подписан ровно на ту ветку, в которой стоит, и переходя в пристёгнутую, выходит из состава приказов прежней и входит в состав приказов новой. Отсюда правило сбора отряда: **приказ движения ждёт только тех, кто уже здесь.** Ждать тех, кто ещё доделывает свою ветку, значило бы, что двое свободных, посланных с Shift вслед за третьим, который строит завод, простоят в первой точке до конца стройки, — со стороны это неотличимо от зависшего приказа.

Границу между двумя обходами держать в голове обязательно: **достижимость по ссылкам решает, когда приказ можно убрать; присутствие в ветке решает, кого ждать.** Ветка, ведущая в общую, отвечает «ждут» на любой её приказ, пока жива, иначе пришедший позже нашёл бы список пустым; но в состав приказов она никого не записывает — участники войдут туда сами, когда действительно перейдут.

Ссылка ставится только в хвост и только вперёд: кольцо означало бы очередь, которая держит саму себя и потому не умрёт никогда. Живость считается по всей достижимости — пристёгнутая ветка жива, пока живы исполнители тех очередей, что в неё ведут, даже если своих подписчиков у неё нет ни одного.

**Приказ части отряда отделяет её в свою очередь** (`Fork`). Пристегнуть ветку к общей цепочке значило бы отдать приказ и тем, кого игрок не выделял, поэтому получатель сперва забирает свой остаток себе. Приказы при этом переносятся ссылками — состояние исполнения у них общее.

**Подход отдельным приказом не ставится.** Прежде рабочий приказ раздавался цепочкой «дойти, потом работать» с точкой подхода у каждого своей; общему списку такой приказ принадлежать не может — в нём место одно, а точек столько же, сколько юнитов. Потери нет: подход был нужен не механике, а показу, и путь по-прежнему виден линией от юнита к месту работы.

Завод раздаёт новорождённым **копии** приказов точки сбора, а не сами приказы: иначе весь отряд встал бы у неё, дожидаясь юнита, которого завод ещё только собирает. Без приказов завод ставит якорь у выезда — юнит остаётся у завода, а не уходит за коммандером. Выезд выбирается по длине пути до цели текущего приказа точки сбора: среди открытых `rolloff_directions` берётся тот, откуда дойти быстрее.

Порядок фаз кадра из этого и следует: мозги (10–15) → исполнитель (20) → экономика (30). Решение, ход и учёт именно в этом порядке, иначе башня заявит спрос на цель, которую только что потеряла.

**Что приказать — решает цель под курсором,** а не заранее выбранный режим: щёлкнули по врагу — атака, по каркасу или плану — стройка, по повреждённому своему — ремонт, по здоровому своему — сопровождение с помощью, по земле — движение. Одна кнопка на всё, как в PA. Разбор идёт от самого определённого к самому общему, и сопровождение стоит предпоследним: щелчок по подбитому своему означает «почини», а не «иди за ним», а тот, кто чинить не умеет, ветку ремонта не примет и дойдёт до сопровождения сам. Ведущим не бывает тот, кто сам выделен, — иначе отряд ходил бы сам за собой.

**Кому приказ уйдёт — решает выделение.** ЛКМ выделяет одного или тянет рамку, Shift добавляет к выделению и дописывает приказ в хвост очереди вместо замены. Не выделено никого — приказ не уходит никому: неявного получателя нет намеренно, потому что панели выделения и приказов при пустом выделении скрыты и объяснить такой приказ интерфейсу было бы нечем. В рамку попадает только то, чем можно управлять: своё и с непустым набором (у склада и стены в наборе есть снос).

**Очередь выделенных рисуется целиком** (`OrderOverlay`) — вся цепочка, а не только текущий шаг: игрок должен видеть, что юнит сделает — дойти, потом строить, — а не гадать по одной ближайшей стрелке. Отдельной нодой поверх мира, потому что приказ это связь между двумя сущностями, и рисовать её у одной из них значит завести у неё знание о том, чего она не касается. Точка шага берётся из положения цели прямо сейчас: враг за это время убежал, и путь обязан тянуться за ним.

### 5.12 Бой: ось, прочность, урон

**Ось «вперёд» есть у любой сущности мира** — интерфейс `IFacing` с одним углом в радианах. Правило единое, а вот воплощение разное, и разница не случайна:

- **Подвижные** (`Unit`) держат два угла. `Rotation` ноды — направление корпуса и движения: его доворачивает `MovementSystem` по фактической скорости. Направление инструмента (ствол или манипулятор) живёт отдельно и совпадает с `IFacing` / `IArmed.Facing`, когда умение задаёт `aim_while_moving`. Иначе ось прицеливания совпадает с корпусом и на ходу не крутится к цели. Скорость доворота берётся из справочника.
- **Здания** ноду НЕ крутят: их визуал привязан к клеткам, а поворот ноды сетку занятости не поворачивает. Направление живёт числом в `footprint.facing_degrees` и рисуется маркером. Задел под турели и ворота.

Надписи и полоски прочности рисуются с компенсацией поворота корпуса (`DrawSetTransform(..., -Rotation, ...)`) — иначе они крутились бы вместе с нодой. Передняя часть инструмента рисуется со сдвигом на его угол относительно корпуса; треугольник на корпусе показывает курс движения.

**Прочность** (`Health`) — обычный C#-объект, которым владеет нода: отдельную ноду на характеристику не заводим. Неуязвимость — не «бесконечное здоровье», а отдельный признак: коммандер урон копит и показывает, но не гибнет, потому что сессия не должна обрываться от зазевавшегося игрока. Полученное считается всегда — на этом и держится его счётчик.

**Цепочка урона намеренно длинная:**

```
WeaponSystem  — остыл ствол? есть цель? довернуть корпус, цель в конусе → выстрел
ProjectileSystem — снаряд летит, ищет попадание по ОТРЕЗКУ за кадр (иначе проскочит цель)
   → документ DamageDealt
DamageSystem (фаза React) — правит прочность, публикует EntityDestroyed, выводит сущность из игры
```

Почему снаряд не бьёт цель сам: в момент его шага по разрезам ходят другие системы, и удаление ноды из-под них рождает висячие ссылки. В фазе `React` кадр уже отработал, и вывести сущность из игры безопасно.

**Цели ищутся одним разрезом** по признаку `IDamageable`, разложенным вдобавок по сторонам (`GM.Targets`). Поэтому «ближайшая постройка ИЛИ каркас ИЛИ юнит» — один обход, чужих не приходится отсеивать поштучно, а новый вид сущности попадает в поиск сам, стоит ему реализовать интерфейс.

**Носители оружия ведут себя одинаково.** Один признак `IArmed` — и дальше всё решает `WeaponSystem`: враг, коммандер и турель проходят один и тот же порядок «остыл → есть цель → в радиусе → довернуть → в конусе → выстрел». Разница между ними только в ответах на два вопроса: `CanFire` (турель и враг стреляют всегда, юнит — без приказов или по приказу атаки) и `FireTarget` (враг бьёт того, к кому шёл; коммандер по приказу — назначенного; турель не выбирает, ей находят ближайшего).

Отсюда же правило доворота: **одну ось крутит кто-то один за кадр.** Корпус на ходу принадлежит `MovementSystem`. Ось прицеливания в пределах дальности крутит `WeaponSystem` (или обработчик работы / ремонта у руки). Два доворота одной и той же оси за кадр удвоили бы скорость вращения.

Рисуют прицел все через `WeaponGizmo` — круг дальности и рёбра конуса. Три копии этого кода в трёх `_Draw` разошлись бы уже через неделю.

**Осторожно с `DrawSetTransform`.** Он действует на всё, что нарисовано ПОСЛЕ него, и «сброс» в конце не спасает соседей по методу: у турели башня и конус разъехались ровно потому, что треугольник рисовался после компенсации поворота основания. Правило: сначала рисуем то, что живёт в координатах ноды, и только потом трогаем трансформ.

**Приказ «атака»** (`OrderKind.Attack`) держит жертву нодой и живёт, пока она жива: пала — приказ снят, и коммандер возвращается к автоогню. Подход к цели — в `Unit`, выстрел — в `WeaponSystem`; ПКМ по врагу даёт приказ, ПКМ по пустому месту — по-прежнему движение.

**Виды врагов — это числа, а не классы**, ровно как роли юнитов: один скрипт `Enemy`, а толстяк и стрелок различаются определением. Ствол вынесен отдельным определением инструмента (`WeaponDefinition`), потому что оружие — самостоятельная вещь: у коммандера тот же тип данных со средними числами.

### 5.13 Сигналы Godot — на границе с представлением

Правило разделения: **внутри симуляции связи идут через документы**, **сигналы — на границе с презентацией** (проекция изменилась → сигнал → полоска ресурса обновилась). Сигналы соединяются и в редакторе, и в коде — это та самая настраиваемость под геймдизайн, и в Godot она родная.

## 6. Журналы: как ужимать и не сломать проекции

Наивный журнал только дописывается и растёт всю сессию. Резать бездумно нельзя: потребители читают по курсору `SequenceId`, а проекции строятся из документов.

**Ключевой принцип:** проекция — это свёртка журнала. Обрезать журнал безопасно только до точки, которую все проекции и потребители уже впитали. Отсюда две дороги: либо сделать проекции независимыми от истории, либо знать «водяной знак» — докуда дошли все.

### Стратегия 1 — инкрементальные проекции (основная)

Проекция обновляет агрегат дельтой в момент дозаписи, а не пересчётом. Тогда её состояние **не зависит от того, лежит запись в журнале или нет** — журнал можно резать свободно. Это дефолт проекта, и пока он соблюдается, обрезка журнала проекции в принципе не задевает.

### Стратегия 2 — фазовая очистка транзиентных записей

Большинство документов нужны только чтобы системы среагировали здесь и сейчас. Помечаем их `[TransientEvent]`, в конце кадра `ClearTransient` чистит такие потоки целиком. Курсоры не нужны. **Сейчас в проекте работает только эта стратегия плюс первая.**

### Стратегия 3 — водяной знак (для записей, живущих дольше кадра)

Если запись читают несколько потребителей в разном темпе, поток держит по курсору на потребителя и режет всё ниже минимального:

```csharp
public void Compact()
{
    int keep = _cursor.Count > 0 ? _cursor.Values.Min() : int.MaxValue;
    _records.RemoveAll(r => r.SequenceId <= keep);
}
```

Нумерация `SequenceId` при чистке **не сбрасывается** — иначе курсоры спутают новую запись со старой.

### Стратегия 4 — снапшоты и усечение (для сохранений)

Периодически снимаем снимок состояния проекций и усекаем журнал до точки снимка. Восстановление = снимок + хвост журнала. Для одиночной игры снимок проекций и есть основа сейва.

### Стратегия 5 — кольцевой буфер

Для потоков с фиксированным горизонтом (нужны последние N событий) — старое затирается новым, роста нет.

### Правило, чтобы проекции не ломались

- **Проекция инкрементальная** — обрезка журнала её не трогает. Так по умолчанию.
- **Если проекция всё же считается из журнала** — усечение обязано идти через водяной знак с её курсором. Порядок: проекция фиксирует свой агрегат снимком → и только потом режем журнал до её курсора. Никогда не режем ниже точки, которую проекция ещё не учла.

## 7. Связывание сущностей

- У каждой сущности **стабильный `EntityId`** (`GameManager.NewId()`).
- **Документы носят `EntityId` и значения, а не ссылки на ноды.** Нода умирает, а документ должен пережить её и сохранение.
- **`EntityStore`** даёт обратный перевод id → нода, когда система отреагировала на документ и ей нужна живая сущность.
- Внутри кадра ноды могут держать прямые ссылки для «горячих» связей. Но всё, что пересекает слои, — только через id.
- **`Owner` (playerId)** на сущности — задел под co-op, даже пока игрок один.

## 8. Подводные камни Godot + C#

Собрано по граблям, на которые уже наступили.

**Освобождённая нода бросает исключение при проверке.** `GodotObject.IsInstanceValid(x)` сам кидает `ObjectDisposedException`, если C#-обёртка уже освобождена. Поэтому любые ссылки на возможно-мёртвые ноды проверяем через `Alive.Is(...)`, а не напрямую.

**Уходящий узел обязан отпустить тех, кто на него ссылается.** `WorkNode.ReleaseWorkers()` вызывается до `QueueFree()`: иначе юнит на следующем кадре обратится к мёртвому объекту. Плюс перед удалением узлу ставится `SetProcess(false)`, чтобы по нему не прошёл ещё один кадр отрисовки. Из разрезов индекса нода выпадает сама — снимать её руками не нужно.

**Id выставляется до добавления в дерево.** Иначе нода успевает получить работу с ещё нулевым `Id` — подключение к узлу работы запишется не на того исполнителя, а отключение потом не сработает и мощность зависнет навсегда.

**Мировые координаты мыши считает только `CursorSystem`.** Экранную позицию она берёт из `InputEventMouseMotion` через `_Input` (не через `_UnhandledInput`: UI не должен останавливать отслеживание) и каждый графический кадр переводит текущим `GetViewport().GetCanvasTransform().AffineInverse()`. `GetGlobalMousePosition()` не используется: системное положение расходится с координатами события. API разделяет фактическую точку (`ActualWorldPosition`), визуальную/прогнозируемую (`VisualWorldPosition`) и точное преобразование позиции кнопки (`WorldFromEvent`). Представление (призрак, конец рамки) читает визуальную; игровые решения по `MouseButton` — только точную позицию события. Экстраполяция по умолчанию выключена, применяется лишь к визуальной точке, скорость считает по собственным меткам событий и не берёт запаздывающую `Input.GetLastMouseVelocity`. Накоплением ввода (`Input.UseAccumulatedInput`) система тоже управляет явно: в сцене по умолчанию оно выключено для проверки задержки.

**Имена полей не должны пересекаться с именами типов.** Поле `Order` в `GameSystem` перекрыло класс `Order` и уронило сборку; поэтому поле называется `StepOrder`. По той же причине вспомогательный поиск предка в `GameSystem` зовётся `Ancestor<T>()`, а не `Owner<T>()`: `Owner` — свойство самой `Node`.

**Control под CanvasLayer не наследует размер слоя.** Якоря выставляются, а опорный прямоугольник остаётся нулевым, и вся разметка схлопывается в левый верхний угол. Поэтому корнем каждого дерева интерфейса служит `UiFrame`: он задаёт себе размер вьюпорта явно и обновляет его по сигналу `SizeChanged`.

**`SetAnchorsPreset` не трогает смещения.** Якоря становятся правильными, а размер остаётся прежним, потому что offsets хранят старый прямоугольник. Для растягивания на родителя нужен `SetAnchorsAndOffsetsPreset`.

**Имя члена класса перекрывает одноимённое пространство имён.** Метод `GameManager.System<T>()` сделал недоступной запись `System.Collections.Generic.List<>` внутри этого же класса — компилятор разбирает `System.` как обращение к члену. Лечится директивой `using` вместо полного имени типа; менять название метода ради этого не потребовалось.

**Снос сессии идёт сверху вниз, а сборка — снизу вверх.** Выход из дерева получает сначала родитель, потом дети; `_Ready`, наоборот, приходит детям раньше родителя. Отсюда два правила: система держит свою ссылку на менеджера (к её `_ExitTree` статической уже нет), а `GameManager.I` обнуляется только если уходит текущий владелец.

**Сессию сносим `RemoveChild` + `QueueFree`, а не одним `QueueFree`.** Освобождение отложено до конца кадра, поэтому новая сессия успела бы встать на место раньше, чем догорела старая, — и уходящий менеджер погасил бы ссылку на живого преемника. Явный вывод из дерева делает выход синхронным и ставит события в верный порядок.

## 10. Состояние и что дальше

**Работает:** единая очередь приказов у всех — ботов, коммандера, врагов, турелей и башен; выделение мышью с рамкой и отрисовка очередей выделенных; приказ по цели под курсором, включая стройку и починку; стройка по сетке с матрицей, каркасы с вытягиванием ресурсов по суммарной мощности, автономный бот-фабрикатор, HUD и панель строительства.

**Работает в экономике:** разовая генерация точек метала с отступом от базы и минимальным расстоянием между ними, экстрактор на точке (энергия → метал), синтезатор как сброс излишков энергии, генераторы двух ступеней, потоковая производительность одна на всю базу.

**Работает в бою:** два вида врагов из справочников, поток врагов с окружности за полем точек, выбор ближайшей цели (постройки, каркасы, юниты, коммандер), доворот корпуса и стрельба в конусе, летящие снаряды, прочность и гибель сущностей, автоогонь коммандера без приказов, приказ «атака» по ПКМ, турель за метал, счёт боя в HUD.

**Турель** — постройка со стволом: стоит по клетке, крутит башню, цель ей находит общая система стрельбы. Единственная постройка, чья ось «вперёд» живёт в `Rotation` ноды.

**Роли юнитов задаются набором инструментов, а не классами:** у коммандера пушка и рука на 20, у фабрикатора одна рука на 4, у башни-сборщика манипулятор на 8 с дальностью в её обзор. Новая роль делается дописыванием строки в `tools`.
*(Мощность руки коммандера удвоена против исходной десятки — чтобы не ждать во время отладки.)*

**Виды врагов — так же числами:** определения в `resources/units/enemies/<id>/`. Новый вид — новая папка, кода не трогая.

**Отложено:**

- Ремонт — в конфиге есть задел, урон в игре уже появился.
- Здание-ассемблер (`class = "assembler"`) — выключено.
- Пафайндинг: растровая карта навигации, A* с полем клиренса, boids для локального обхода; заодно свободная постановка зданий вместо сетки. Сейчас юниты ходят по прямой и сквозь здания. Решение расписано в [pathfinding.md](pathfinding.md).
- Сохранения — снимок проекций плюс сущности; тогда же часть документов перестанет быть транзиентной.
- Сеть и мультиплеер — документы естественные кандидаты на репликацию, когда вернёмся.
