# Практические заметки по редактору контента

Этот файл фиксирует неочевидные особенности Godot и принятые решения, которые уже
приводили к дефектам при разработке `addons/content_editor/`. Его следует дополнять,
когда исправление требует знания о жизненном цикле редактора, сигналах, импорте ресурсов
или формате TOML, которое нельзя непосредственно вывести из интерфейса класса.

## Жизненный цикл EditorPlugin

### `_MakeVisible` может предшествовать `_Ready`

Godot может вызвать `_MakeVisible` сразу после добавления главного `Control`, когда его
дочерние элементы ещё не созданы. Публичный вход не должен обращаться к `_form`,
`_preview`, `_balance` и другим полям напрямую. Сначала вызывается
`ContentEditorMain.EnsureOperational()`, который идемпотентно создаёт UI, связывает его
со Store и загружает каталог.

Проверки только флага `_uiBuilt` недостаточно: после перезагрузки C# managed-поля могут
быть созданы заново, тогда как нативные узлы ещё остаются в дереве. Поэтому готовность
определяется одновременно по `ContentEditorLifecycle`, `GodotObject.IsInstanceValid`
для обязательных узлов и MVID текущей сборки.

### Сборка C# не равна обычному изменению файла

`EditorFileSystem.FilesystemChanged` не гарантирует уведомление о новой DLL. Главный
экран дополнительно проверяет время изменения загруженной сборки. Состояние открытых
вкладок сохраняется в `.godot/content_editor_workspace.cfg`, поскольку managed-объекты
и их черновики могут быть уничтожены при перезагрузке сборки.

Снимок необходимо записывать при каждом изменении Store, а читать до
`ReloadFromDisk()`: сама загрузка вызывает `Changed` и иначе может заменить сохранённый
снимок пустым состоянием.

Для снимка используется Godot `ConfigFile`, а не `System.Text.Json`. `System.Text.Json`
кэширует сведения о типах и является известной причиной `Failed to unload assemblies`
в tool-коде Godot. Общий `AssemblyUnloadCleanup` дополнительно очищает этот кэш перед
выгрузкой `AssemblyLoadContext`, поскольку JSON используется и в игровых системах.

При `_ExitTree` узлы плагина освобождаются синхронно через `Free()`. `QueueFree()` ждёт
конца кадра, тогда как выгрузка сборки может начаться раньше и обнаружить ещё
подключённые managed-делегаты.

### `Reparent` нельзя считать обычной выгрузкой

При переносе главного экрана в отдельное `Window` узел может кратковременно получить
`_ExitTree`. Обычный `_ExitTree` переводит редактор в `Disposed`, но при таком переносе
Store уничтожать нельзя. Перенос выполняется только через
`ContentEditorMain.ReparentWithoutShutdown()`, который на время операции устанавливает
отдельный признак.

Перед освобождением полноэкранного окна главный экран необходимо сначала вернуть в
`EditorMainScreen` либо явно завершить его работу. Освобождение окна вместе с дочерним
главным экраном уничтожит открытые вкладки.

## Сигналы и отложенные вызовы

### Нельзя отключать сигнал без существующего соединения

Операция `event -= handler` для сигналов Godot не является безусловно безопасной:
движок выводит ошибку `Attempt to disconnect a nonexistent connection`. Плагин хранит
отдельный признак успешной подписки и отключает обработчик только при установленном
соединении. Повторное включение плагина и смена экземпляра `EditorFileSystem` должны
обрабатываться отдельно.

### Отложенный обработчик может относиться к старому UI

`CallDeferred` исполняется после текущего обхода дерева. К этому моменту C#-сборка или
весь UI могут быть пересозданы. Для вызова используется `Node.CallDeferred` с именем
метода, а не `Callable.From(lambda)`: очередь SceneTree не должна хранить managed-делегат
во время выгрузки. Обработчик проверяет `IsInstanceValid`, состояние `Disposed` и номер
поколения UI.

Store может измениться внутри сигнала `LineEdit`, `OptionButton` или `ColorPickerButton`.
Немедленное удаление и повторное создание этих элементов из того же сигнала нарушает
состояние активного элемента. Поэтому общая перерисовка формы объединяется в один
отложенный вызов.

### Пользовательские кнопки диалога не всегда закрывают его

Кнопка, добавленная через `AcceptDialog.AddButton` с пользовательским действием,
испускает `CustomAction`, но не обязана скрывать диалог. Перед показом следующего
конфликта диалог скрывается явно. Идентификаторы ожидающих конфликтов хранятся также в
`HashSet`, поскольку сигналы файловой системы и возврат фокуса могут несколько раз
сообщить об одном файле.

## TOML и внешние изменения

### Полная сериализация уничтожает полезное оформление

Tomlyn 0.17 при обратной сериализации меняет порядок ключей и не сохраняет все
комментарии. Редактор не сериализует всю таблицу: `TomlPatchWriter` заменяет или удаляет
конкретную строку и удаляет только опустевшую секцию.

Перед записью изменённый набор текстов компилируется целиком. Запись выполняется через
временный файл, после чего обновляются метка времени сессии и глобальный каталог.

### Метка происхождения должна содержать путь

Одного перечисления `Local/Base/Vars/Default` недостаточно для интерфейса. Для каждого
поля Store возвращает `FieldSourceInfo` с понятным видом происхождения и путём к файлу,
где найден ключ. По этому пути форма открывает родительское определение в новой вкладке,
а `*.vars.toml` — в контекстной панели значений.

Путь следует искать в сырой цепочке `base`. После `TomlResolver.Resolve` ссылка на
`*.vars.toml` уже заменена итоговым числом, поэтому определить фактический источник по
разрешённой таблице невозможно.

### Удаление файла является отдельным внешним изменением

`FileStamp == 0` означает не отсутствие изменений, а возможное удаление файла. Чистая
сессия принимает удаление и закрывается. Для сессии с черновиком показывается конфликт:
пользователь может принять удаление либо оставить черновик и позднее восстановить файл
командой «Применить».

## Ресурсы и отрисовка

### `Image.Load("res://...")` непригоден для экспортируемых ресурсов

Прямое чтение исходного PNG работает в редакторе, но Godot предупреждает, что файл не
будет доступен в экспортированной игре. Спрайты загружаются через
`ResourceLoader.Load<Texture2D>()`. Если требуется анализ альфа-канала, изображение
получается через `Texture2D.GetImage()`.

Это правило относится и к основной текстуре, и к вспомогательным вычислениям, например
к `SpriteOcclusion`: один прямой вызов на каждом пути создавал два одинаковых
предупреждения при выборе юнита.

### Предпросмотр должен использовать производственную отрисовку

Поле сравнения вызывает `UnitSilhouette`, `BuildingVisual`, `VisionGizmo`,
`WeaponGizmo` и `WorkGizmo`, но не создаёт игровые сущности. Отдельная упрощённая
отрисовка быстро расходится с игрой по масштабу, повороту спрайта и слоям здания.

Производственный метод может сам вызвать `DrawSetTransform`, поскольку в игре объект
обычно рисуется около локального `(0, 0)`. Предпросмотр не должен рассчитывать, что
назначенная им внешняя трансформация сохранится. Экранные `origin` и масштаб передаются
в `BuildingVisual.Draw` / `UnitSilhouette.Draw` явно; методы спрайта получают тот же
`baseOrigin`. Иначе спрайт и последующая обводка появляются в левом верхнем углу.

### Граф рисует рёбра и подписи отдельными проходами

Если каждое ребро сразу рисует линию и подпись, линия следующего ребра может пройти
поверх уже нарисованного текста. Сначала рисуются все маршруты, затем все непрозрачные
фоны и подписи, после чего — узлы.

Для уменьшения пересечений узлы распределяются по топологическим уровням и сортируются
по средней позиции родительских узлов. Соседние уровни соединяются ортогональными
маршрутами в промежутках между колонками; длинные рёбра выводятся в свободный коридор
над узлами.

## Компоновка интерфейса

### Повторяемые элементы следует выделять в примитивы

Классы в `addons/content_editor/primitives/` не знают о жизненном цикле
`ContentEditorMain` и выполняют одну задачу:

- `EditorPropertyRow` размещает название, редактор значения и действия в три колонки
  либо переносит длинный редактор под заголовок;
- `EditorContextTabs` управляет закрываемыми страницами и позволяет сохранить их при
  смене идентификатора контекста; главный экран решает, какие страницы применимы к
  новой сущности;
- `EditorKeyValueTable` показывает справочные наборы ключей;
- `EditorNodeGraph` рисует типизированные узлы и связи на сетке.

Предметные решения — какой vars-файл открыть, какие зависимости построить и какой
`ActiveSession` допустим — остаются в Store, форме и главном экране. Примитив не должен
самостоятельно читать TOML или обращаться к глобальному каталогу.

`EditorMainScreen` не является обычным `Container` для дочернего элемента плагина.
Одних `SizeFlags.ExpandFill` недостаточно: после `AddChild` задаётся
`SetAnchorsAndOffsetsPreset(LayoutPreset.FullRect)`.

Свойство формы должно иметь единый визуальный блок из заголовка, происхождения,
кнопок действий и поля ввода. Отдельные подписи без общего фона воспринимаются как
относящиеся к соседним элементам. Технические `base` и `vars` в пользовательском
интерфейсе не показываются; используются подписи «унаследовано» и
«из файла переменных».

Для вкладок открытых сущностей используется `TabBar` с нативной кнопкой закрытия.
Отдельные кнопки названия и закрытия не обеспечивают однозначной связи при нескольких
открытых сущностях.

## Минимальная проверка после изменений

1. Выполнить `dotnet build red_planet.csproj`.
2. Выполнить `dotnet run --project tools/ContentEditorTests`.
3. Открыть вкладку «Контент» до и после C#-сборки.
4. Проверить сохранение грязного черновика после сборки.
5. Изменить и удалить открытый TOML-файл внешним редактором.
6. Перенести редактор в полноэкранное окно и вернуть его во вкладку.
7. Открыть юнита со спрайтом и проверить журнал на отсутствие предупреждений
   `Loaded resource as image file`.
