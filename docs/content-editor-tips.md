# Практические заметки по редактору контента

Этот файл фиксирует неочевидные особенности Godot и принятые решения, которые уже
приводили к дефектам при разработке `addons/content_editor/`. Его следует дополнять,
когда исправление требует знания о жизненном цикле редактора, сигналах, импорте ресурсов
или формате TOML, которое нельзя непосредственно вывести из интерфейса класса.

## Жизненный цикл EditorPlugin

### `_MakeVisible` может предшествовать `_Ready`

Godot может вызвать `_MakeVisible` сразу после добавления главного `Control`, когда его
дочерние элементы ещё не созданы. Публичный вход не должен обращаться к `_form`,
`_preview`, `_balance` и другим полям напрямую. Сначала вызывается
`ContentEditorMain.EnsureOperational()`, который идемпотентно создаёт UI, связывает его
со Store и загружает каталог.

Готовность определяется по `ContentEditorLifecycle` и `GodotObject.IsInstanceValid`
для обязательных узлов. Флага `_uiBuilt` недостаточно: узел мог быть освобождён, тогда
как флаг ещё истинен.

### Сборка C# выгружает дерево плагина целиком

Узлы типов из игровой DLL нельзя оставлять в дереве редактора на время выгрузки
`AssemblyLoadContext`: редактор падает с обращением по недопустимому адресу. Плагин
не переживает перезагрузку на том же нативном `Control`. `_ExitTree` освобождает дерево
безусловно и ищет узлы по имени, потому что managed-поле к этому моменту может быть
уже обнулено. `_EnterTree` не подключает остаточный узел заново, а освобождает его
и строит экран с нуля.

Открытые вкладки, черновики и настройка режимов возвращаются из
`.godot/content_editor_workspace.cfg`. Снимок необходимо записывать при каждом изменении
Store, а читать до `ReloadFromDisk()`: сама загрузка вызывает `Changed` и иначе может
заменить сохранённый снимок пустым состоянием.

Для снимка используется Godot `ConfigFile`, а не `System.Text.Json`. `System.Text.Json`
кэширует сведения о типах и является известной причиной `Failed to unload assemblies`
в tool-коде Godot. Общий `AssemblyUnloadCleanup` дополнительно очищает этот кэш перед
выгрузкой `AssemblyLoadContext`, поскольку JSON используется и в игровых системах.

При `_ExitTree` узлы плагина освобождаются синхронно через `Free()`. `QueueFree()` ждёт
конца кадра, тогда как выгрузка сборки может начаться раньше и обнаружить ещё
подключённые managed-делегаты. Остаточный узел с тем же именем тоже освобождается
через `Free()`: иначе новый `AddChild` столкнулся бы с занятым именем до конца кадра.

### `Reparent` нельзя считать обычной выгрузкой

При переносе главного экрана в отдельное `Window` узел может кратковременно получить
`_ExitTree`. Обычный `_ExitTree` переводит редактор в `Disposed`, но при таком переносе
Store уничтожать нельзя. Перенос выполняется только через
`ContentEditorMain.ReparentWithoutShutdown()`, который на время операции устанавливает
отдельный признак.

Перед освобождением полноэкранного окна главный экран необходимо сначала вернуть в
`EditorMainScreen` либо явно завершить его работу. Освобождение окна вместе с дочерним
главным экраном уничтожит открытые вкладки.

## Сигналы и отложенные вызовы

### Нельзя отключать сигнал без существующего соединения

Операция `event -= handler` для сигналов Godot не является безусловно безопасной:
движок выводит ошибку `Attempt to disconnect a nonexistent connection`. Плагин хранит
отдельный признак успешной подписки и отключает обработчик только при установленном
соединении. Повторное включение плагина и смена экземпляра `EditorFileSystem` должны
обрабатываться отдельно.

### Отложенный обработчик может относиться к старому UI

`CallDeferred` исполняется после текущего обхода дерева. К этому моменту C#-сборка или
весь UI могут быть пересозданы. Для вызова используется `Node.CallDeferred` с именем
метода, а не `Callable.From(lambda)`: очередь SceneTree не должна хранить managed-делегат
во время выгрузки. Обработчик проверяет `IsInstanceValid`, состояние `Disposed` и номер
поколения UI.

Store может измениться внутри сигнала `LineEdit`, `OptionButton` или `ColorPickerButton`.
Немедленное удаление и повторное создание этих элементов из того же сигнала нарушает
состояние активного элемента. Поэтому общая перерисовка формы объединяется в один
отложенный вызов.

### Пользовательские кнопки диалога не всегда закрывают его

Кнопка, добавленная через `AcceptDialog.AddButton` с пользовательским действием,
испускает `CustomAction`, но не обязана скрывать диалог. Перед показом следующего
конфликта диалог скрывается явно. Идентификаторы ожидающих конфликтов хранятся также в
`HashSet`, поскольку сигналы файловой системы и возврат фокуса могут несколько раз
сообщить об одном файле.

## TOML и внешние изменения

### Полная сериализация уничтожает полезное оформление

Tomlyn 0.17 при обратной сериализации меняет порядок ключей и не сохраняет все
комментарии. Редактор не сериализует всю таблицу: `TomlPatchWriter` заменяет или удаляет
конкретную строку и удаляет только опустевшую секцию.

Перед записью изменённый набор текстов компилируется целиком. Запись выполняется через
временный файл, после чего обновляются метка времени сессии и глобальный каталог.

### Метка происхождения должна содержать путь

Одного перечисления `Local/Base/Vars/Default` недостаточно для интерфейса. Для каждого
поля Store возвращает `FieldSourceInfo` с понятным видом происхождения и путём к файлу,
где найден ключ. По этому пути форма открывает родительское определение в новой вкладке,
а `*.vars.toml` — в контекстной панели значений.

Путь следует искать в сырой цепочке `base`. После `TomlResolver.Resolve` ссылка на
`*.vars.toml` уже заменена итоговым числом, поэтому определить фактический источник по
разрешённой таблице невозможно.

### Удаление файла является отдельным внешним изменением

`FileStamp == 0` означает не отсутствие изменений, а возможное удаление файла. Чистая
сессия принимает удаление и закрывается. Для сессии с черновиком показывается конфликт:
пользователь может принять удаление либо оставить черновик и позднее восстановить файл
командой Apply.

## Ресурсы и отрисовка

### `Image.Load("res://...")` непригоден для экспортируемых ресурсов

Прямое чтение исходного PNG работает в редакторе, но Godot предупреждает, что файл не
будет доступен в экспортированной игре. Спрайты загружаются через
`ResourceLoader.Load<Texture2D>()`. Если требуется анализ альфа-канала, изображение
получается через `Texture2D.GetImage()`.

Это правило относится и к основной текстуре, и к вспомогательным вычислениям, например
к `SpriteOcclusion`: один прямой вызов на каждом пути создавал два одинаковых
предупреждения при выборе юнита.

### Предпросмотр должен использовать производственную отрисовку

Поле сравнения вызывает `UnitSilhouette`, `BuildingVisual`, `VisionGizmo`,
`WeaponGizmo` и `WorkGizmo`, но не создаёт игровые сущности. Отдельная упрощённая
отрисовка быстро расходится с игрой по масштабу, повороту спрайта и слоям здания.

Производственный метод может сам вызвать `DrawSetTransform`, поскольку в игре объект
обычно рисуется около локального `(0, 0)`. Предпросмотр не должен рассчитывать, что
назначенная им внешняя трансформация сохранится. Экранные `origin` и масштаб передаются
в `BuildingVisual.Draw` / `UnitSilhouette.Draw` явно; методы спрайта получают тот же
`baseOrigin`. Иначе спрайт и последующая обводка появляются в левом верхнем углу.

### Граф рисует рёбра и подписи отдельными проходами

Если каждое ребро сразу рисует линию и подпись, линия следующего ребра может пройти
поверх уже нарисованного текста. Сначала рисуются все маршруты, затем все непрозрачные
фоны и подписи, после чего — узлы.

Для уменьшения пересечений узлы распределяются по топологическим уровням и сортируются
по средней позиции родительских узлов. Соседние уровни соединяются ортогональными
маршрутами в промежутках между колонками; длинные рёбра выводятся в свободный коридор
над узлами.

## Компоновка интерфейса

### Повторяемые элементы следует выделять в примитивы

Классы в `addons/content_editor/primitives/` не знают о жизненном цикле
`ContentEditorMain` и выполняют одну задачу:

- `EditorPropertyRow` размещает название, редактор значения и действия в три колонки
  либо переносит длинный редактор под заголовок;
- `EditorContextTabs` управляет закрываемыми страницами и позволяет сохранить их при
  смене идентификатора контекста; главный экран решает, какие страницы применимы к
  новой сущности;
- `EditorKeyValueTable` показывает справочные наборы ключей;
- `EditorNodeGraph` рисует типизированные узлы и связи на сетке;
- `EditorPanel` даёт области рамку, заголовок и полосу действий в заголовке;
- `EditorFieldEditor` строит виджет правки по `ContentFieldSpec` и разбирает ввод;
- `EditorIdListField` правит список идентификаторов выбором из перечня.

Предметные решения — какой vars-файл открыть, какие зависимости построить и какой
`ActiveSession` допустим — остаются в Store, форме и главном экране. Примитив не должен
самостоятельно читать TOML или обращаться к глобальному каталогу.

`EditorMainScreen` не является обычным `Container` для дочернего элемента плагина.
Одних `SizeFlags.ExpandFill` недостаточно: после `AddChild` задаётся
`SetAnchorsAndOffsetsPreset(LayoutPreset.FullRect)`.

Свойство формы должно иметь единый визуальный блок из заголовка, происхождения,
кнопок действий и поля ввода. Отдельные подписи без общего фона воспринимаются как
относящиеся к соседним элементам. Технические `base` и `vars` в пользовательском
интерфейсе не показываются; используются подписи «унаследовано» и
«из файла переменных».

Для вкладок открытых сущностей используется `TabBar` с нативной кнопкой закрытия.
Отдельные кнопки названия и закрытия не обеспечивают однозначной связи при нескольких
открытых сущностях.

### Кнопка должна стоять в области своего действия

Действия над активной сущностью (`Apply`, `Revert`, `Reload file`, `Close`) находятся
в полосе под вкладками сущностей, и первым элементом этой полосы стоит имя файла.
Пока те же кнопки стояли в верхней полосе рядом с `Reload`, по их расположению нельзя
было определить, относятся они к проекту или к выбранной вкладке. По той же причине
`Layout` перенесён на панель измерительного поля: он переставляет объекты поля.

Кнопка, нажатие на которую ничего не изменит, выключается: `Apply` и `Revert` — при
отсутствии несохранённых правок, `Fit all` — при пустом поле, `Layout` — при
единственной открытой сущности, подтверждение диалога сохранения вида — при пустом
имени. Подсказка выключенной кнопки называет причину, иначе выключенное состояние
воспринимается как неисправность.

### Один разбор значения на все формы

Форма свойств и инспектор волн правят одни и те же типы значений. Пока разбор чисел
и списков был приватным методом формы, вторая форма означала бы вторую копию, которая
разошлась бы с первой при первом же исправлении. `EditorFieldEditor` содержит только
соответствие «тип значения — виджет»; куда записать результат, решает вызывающая сторона
через обратный вызов.

### Массивы таблиц правятся по номеру блока

Блоков `[[unit_list]]` в файле несколько, и различает их только порядок, поэтому
`TomlPatchWriter` обращается к ним по номеру: `SetArrayItemKey`, `RemoveArrayItemKey`,
`AddArrayItem`, `RemoveArrayItem`. Правка ключа сохраняет прочие строки блока и его
комментарии; удаляется блок вместе с пояснением непосредственно над заголовком,
поскольку такое пояснение относится именно к нему.

Прежнее выражение заголовка секции не различало `[name]` и `[[name]]`, отчего строки
внутри блока считались продолжением корня файла, и корневой ключ мог быть записан внутрь
блока. Проверка `root key stops at table array` закрывает этот случай.

### Разбор для показа должен быть снисходительнее сборки

`ContentCompiler` отбрасывает волну целиком при любой ошибке проверки. Если бы карта волн
читала только собранный каталог, строка исчезала бы посреди правки: пустой список видов
и доля вне пределов — обычные промежуточные состояния. Поэтому `ContentEditorStore`
держит отдельный снисходительный разбор черновиков (`WaveOverviews`), а собранный каталог
отвечает лишь за то, можно ли записать файл: `Apply` по-прежнему отказывается писать
черновик, не прошедший проверки.

### Имена `EditorIcons` следует проверять до запроса

Состав темы редактора меняется между версиями Godot, а запрос отсутствующей иконки
даёт ошибку темы и знак-заглушку на кнопке. `ContentEditorTheme.Icon` сначала
спрашивает `HasThemeIcon` и возвращает `null`, если имени нет; `IconAny` перебирает
несколько имён. Кнопка в этом случае остаётся с одним текстом, и интерфейс
работоспособен на любой версии.

## Разделение ответственности внутри редактора

### Режим обязан следовать общему договору

Главный экран не знает устройства режимов и работает с ними через
`IContentEditorMode`: связывание со Store, обновление, снятие и восстановление состояния,
события `UiStateChanged`, `StatusReported` и `EntityOpenRequested`. Пока каждый режим имел
собственный набор методов, добавление режима требовало правки главного экрана в нескольких
местах, а забытый вызов обнаруживался пропавшей настройкой.

Событие договора, ненужное конкретному режиму, оставляется с подавлением `CS0067`
и пояснением: режим сущностей сам является целью `EntityOpenRequested`, а таблица баланса
ничего не пишет на диск и потому не сообщает в строку состояния.

### Сессия принадлежит области, а не общему перечню

Волна правится в режиме `Waves` и сущностью каталога не является. Пока сессии всех видов
лежали в одном перечне, выбор волны на карте открывал вкладку в режиме `Entities`
и подменял там активную сущность. `ContentEditorScope` разделяет перечни вкладок
и активную сессию; тексты, черновики и сборка каталога остаются общими.

### Колонка таблицы объявляется один раз

Прежде колонка баланса описывалась трижды: в перечне, в `switch` заполнения ячейки
и в `switch` сравнения. Забытая ветвь сравнения давала колонку, которая молча
не сортируется. `BalanceColumn` содержит и способ показать значение, и способ сравнить его.

### Строка правки поля общая для всех форм

Форма свойств, инспектор волн и блоки `[[unit_list]]` строят одну и ту же строку через
`EditorFieldRow` по описанию `EditorFieldRowSpec`. Различаются они только меткой
происхождения и набором действий, а раскладка, разбор ввода и вид кнопки возврата
совпадают по построению.

## Устойчивость

### Исключение из обработчика сигнала прерывает обход дерева

Обработчик сигнала Godot исполняется внутри обхода дерева узлов. Вылетевшее оттуда
исключение оставляет часть виджетов необновлённой, и редактор выглядит зависшим, причём
запись в журнале не связана видимым образом с нажатой кнопкой. Обработчики редактора
вызываются через `EditorControls.Run`, который называет действие, пишет исключение
в журнал и выводит причину в строку состояния главного экрана.

### Разбор TOML кэшируется по тексту

Одно обновление формы вычисляет происхождение для каждого поля, а каждое такое вычисление
разбирает черновик целиком и обходит цепочку `base`. Для файла в двести строк и формы
в полсотни полей это давало десятки разборов на кадр. `TomlText` хранит соответствие
«текст → таблица»: ключом служит сам текст, поэтому правка черновика даёт промах
и повторный разбор, а устаревших данных не бывает. Размер кэша ограничен, так как каждый
набранный символ порождает новый ключ.

### Снимок пишется с отсрочкой

`Store.Changed` приходит на каждое изменение черновика, то есть на каждый набранный символ.
Немедленная запись снимка означала бы десятки обращений к диску в секунду, поэтому запись
откладывается на доли секунды и объединяет подряд идущие изменения. При завершении работы
и перед пересозданием интерфейса снимок пишется немедленно.

### Ресурс настройки может отсутствовать

Панель формы волны читает `resources/tuning/world.tres` и `waves.tres`. Отсутствие файла
не является отказом: подставляются умолчания класса, и панель остаётся работоспособной.
`WaveSettings.ShapeOf` берёт `WaveStart` из `World.Settings`, поэтому перед подсчётом туда
подставляется прочитанный ресурс — так же поступает стенд `SessionPreview`.

### `SplitContainer.SplitOffset` объявлен устаревшим

В Godot 4.7 у области несколько разделителей, и одиночное свойство даёт предупреждение
`CS0618`. Редактору достаточно первого разделителя, поскольку все его области содержат
ровно две части; обращение к нему собрано в `EditorControls.SplitOffset`
и `EditorControls.SetSplitOffset`.

## Настроечные ресурсы

### Ресурс не знает, кому он назначен

Назначение живёт в сцене партии: `Session.tscn` присваивает `terror.tres`, `pressure.tres`
и `waves.tres` свойствам `Settings` соответствующих узлов. Поэтому действующий вариант
определяется чтением сцены (`TuningSceneBinding`), а не путём файла, и переключение на
другой вариант есть правка сцены, а не ресурса.

Опорой служит имя узла и имя свойства. Путь файла опорой быть не может — он как раз
и меняется; идентификатор `ExtResource` тоже не годится, поскольку движок вправе
перенумеровать внешние ресурсы при сохранении сцены.

### Правка сцены выполняется текстом

Загрузка `PackedScene`, создание экземпляра, правка свойства и обратная упаковка
перестраивают файл целиком. Сцена партии содержит несколько десятков узлов, к которым
редактор контента отношения не имеет, поэтому заменяется одна строка, как это сделано
для TOML. Правила замены вынесены в `TuningSceneText` без обращений к Godot и проверяются
`tools/ContentEditorTests`.

Якорь конца строки в этих выражениях записан как `\r?$`: файл сцены может быть сохранён
с окончаниями строк Windows, и без явного возврата каретки выражение не срабатывает.

### Копия ресурса нужна и при записи поверх

Загруженный экземпляр ресурса разделяется с инспектором Godot. Правка черновика не должна
проявляться в инспекторе до записи, поэтому значения наносятся на `Duplicate(true)`,
и уже копия сохраняется. Перед сохранением копии задаётся `ResourcePath` и вызывается
`TakeOverPath`: иначе сохранение варианта переписало бы исходный файл.

### Новый файл нужно показать движку до ссылки на него

После `ResourceSaver.Save` вариант ещё не импортирован. Ссылка из сцены на неимпортированный
файл приводит к предупреждению при следующем открытии сцены, поэтому между записью
и заменой ссылки вызывается обход файловой системы редактора.

### Комментарии исходника — единственный источник пояснений

XML-комментарии над `[Export]` в собранную сборку не попадают: компилятор C# сохраняет их
лишь в отдельный файл документации, который проектом не собирается. Подсказки полей читает
`TuningDocReader` из самого исходника скрипта, путь к которому известен от ресурса.
Отсутствие файла или неожиданное оформление означает подпись без пояснения, а не отказ.

## Минимальная проверка после изменений

1. Выполнить `dotnet build red_planet.csproj`.
2. Выполнить `dotnet run --project tools/ContentEditorTests`.
3. Открыть вкладку Content и выполнить C#-сборку при открытом редакторе: редактор
   не должен завершиться аварийно, вкладка восстанавливается из снимка.
4. Проверить, что грязный черновик после сборки вернулся из снимка.
5. Изменить и удалить открытый TOML-файл внешним редактором.
6. Перенести редактор в полноэкранное окно и вернуть его во вкладку.
7. Открыть юнита со спрайтом и проверить журнал на отсутствие предупреждений
   `Loaded resource as image file`.
8. Проверить режим Waves: выбор волны, ползунок террора, переключатель Log scale.
9. Изменить в инспекторе волны `terror_range`, добавить и удалить блок `[[unit_list]]`,
   применить и убедиться, что комментарии соседних блоков остались на месте.
10. Убедиться, что выбор волны на карте не создаёт вкладки в режиме Entities.
11. Изменить в секции `[spawn]` угол дуги и число очагов и убедиться, что панель формы
    волны перестроилась.
12. Закрыть и открыть редактор: должны восстановиться режим, отбор каталога, представление
    баланса с шириной колонок и фильтрами, а также положения разделителей.
13. Проверить режим Globals: правку числа с последующими **Revert** и **Apply**, сохранение
    варианта и возврат к исходному ресурсу, переход в инспектор для кривой.
14. После сохранения варианта убедиться, что `Session.tscn` ссылается на него, а прочие
    её узлы остались нетронутыми (`git diff scenes/Session.tscn`).
